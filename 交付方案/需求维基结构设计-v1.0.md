# 需求 Wiki 结构设计

## 1. 设计目标

需求 Wiki 不只是“文档目录”，而是同时服务三类消费者的知识系统：

1. **AI Agent**：按需、分层、可验证地消费最小必要上下文，避免一次性注入整站内容。
2. **需求工程师 / 产品经理**：按业务域理解产品逻辑、需求演进、规则边界与交付验收。
3. **知识 Owner / 治理者**：能够确认、复审、追踪来源、处理矛盾与过期知识。

因此采用“**知识本体 + 消费地图 + 学习旅程**”三平面结构：

| 平面 | 载体 | 作用 | 是否频繁变化 |
|---|---|---|---|
| 知识本体 | 业务域、术语、规则、流程、需求、FAQ、决策 | 表达产品需求知识库的稳定事实与逻辑 | 随需求版本变化 |
| 消费地图 | `_agent-manifest.yaml`、`_index.md`、摘要区 | 供 AI 与人渐进式披露、检索与导航 | 随知识结构变化 |
| 学习旅程 | 11 步交互式攻坚路径 | 采用指定学习方法，把知识转化为能力 | 随个人学习进度变化 |

> **关键边界**：学习进度、重试次数、人工确认记录属于运行时状态，建议存储在应用侧或 `learning_state` 数据表中，不直接写入共享 Wiki 正文，避免个人学习状态污染团队知识本体。

## 2. 总体目录结构

## 3. AI 渐进式披露协议

### 3.1 六层披露模型

AI Agent 消费 Wiki 时默认从 L0 开始，不允许直接读取所有正文。

| 层级 | 内容 | 典型大小 | 消费时机 |
|---|---|---|---|
| L0 | 空间 manifest：产品线、权限、域清单、状态、版本 | 极小 | 每次任务初始化 |
| L1 | 空间/域首页：业务地图、知识范围、当前基线 | 小 | 判断目标域与阅读路径 |
| L2 | `_domain-context.md`：域内摘要、核心规则、术语、风险 | 小到中 | 生成需求、问答、影响分析的首选上下文 |
| L3 | 具体知识页：完整规则、流程、需求条目、验收标准 | 中 | 需要精确定义、边界、例外、演进时 |
| L4 | 证据层：KO、原文 chunk、表格、截图、引用定位 | 按需 | 需要审计、争议裁决、可信度验证时 |
| L5 | 学习旅程：方法、练习、输出物、确认门 | 按需 | 用户进入学习或训练场景时 |

### 3.2 Agent 检索决策流

```text
任务输入
  ↓
1. 读取 L0 _agent-manifest.yaml
  ├─ 校验产品线、权限、知识状态、当前有效版本
  └─ 定位候选业务域
  ↓
2. 读取 L1 域 _index.md
  ├─ 判断域是否命中
  └─ 获取页面类型与链接索引
  ↓
3. 读取 L2 _domain-context.md
  ├─ 若摘要足以回答/生成 → 输出并附来源
  └─ 若缺少边界/例外/演进 → 进入 L3
  ↓
4. 读取 L3 具体页面
  ├─ 优先 confirmed / active 页面
  ├─ 术语页 + 规则页 + 需求页可组合成上下文包
  └─ 对存在 conflict / uncertain 标记的页面进入 L4
  ↓
5. 读取 L4 证据
  ├─ 输出证据链与可信度
  └─ 无法确认时明确拒答或标记假设
```

## 4. 页面类型与命名规范

| 类型 | 命名 | 解决的问题 | 必备小节 |
|---|---|---|---|
| 术语 | `术语-{名称}.md` | 统一口径 | 定义、别名、适用范围、与其他术语差异、来源 |
| 规则 | `规则-{名称}.md` | 表达业务约束 | 触发条件、动作、例外、边界、生效版本、来源 |
| 流程 | `流程-{名称}.md` | 表达跨角色时序 | 参与者、前置条件、主流程、分支、异常流、验收 |
| 需求 | `需求-{ID}.md` | 承载需求条目 | 背景、目标、范围、功能需求、验收标准、演进 |
| 场景 | `场景-{名称}.md` | 表达具体使用情境 | 角色、情境、输入、动作、结果、例外 |
| 风险 | `风险-{名称}.md` | 表达业务与交付风险 | 风险、触发条件、影响、缓解措施、责任人 |
| FAQ | `FAQ-{问题}.md` | 沉淀高频问答 | 问题、结论、适用范围、证据、更新时间 |
| 决策 | `决策-{主题}.md` | 保留需求取舍 | 背景、可选方案、决策、理由、影响、时间 |
| 演进 | `演进-{ID或主题}.md` | 复杂版本历史 | 版本时间线、变化点、原因、影响、旧版处置 |

页面正文统一采用“**摘要优先、细节居中、证据最后**”的结构，保证 Agent 可以截断读取而不丢失主结论。

## 6. 11 步交互式学习旅程

学习旅程位于 `50-学习旅程/`，是知识消费视图，不改变知识本体。每条路径可绑定一个业务域、一个角色或一个需求专题。

### 6.1 全局流程

```text
第 1 步 动态专家 STORM 拆解
  → 第 2 步 矛盾与盲区清单
  → 第 3 步 精炼行动简报
  → 第 4 步 可信度同行评审
  → 第 5 步 精选资源策展
  → 第 6 步 5 阶学习阶梯
  → 第 7 步 20 小时核心攻坚与 SOP 实战
  → 第 8 步 毒舌场景压力测试
  → 第 9 步 费曼人机循环教学
  → 第 10 步 战地一页速查表
  → 第 11 步 艾宾浩斯 15 核心闪卡
```

### 6.2 步骤状态机

每个学习会话维护独立状态：

```yaml
learning_session:
  session_id: LS-20261103-ORDER-001
  learner: 王五
  path: 50-学习旅程/路径-退款需求攻坚.md
  domain: 10-订单
  current_step: 3
  step_status: awaiting_confirmation
  retry_count: 0
  max_retries: 5
  confirmed_at: null
  evidence:
    - step: 1
      artifact: 交付方案/订单需求攻坚学习输出-v1.md
      self_check_score: 92
      human_confirmation: true
```

状态流转：

```text
not_started
  → generating
  → self_checking
  → passed
  → awaiting_confirmation
  → confirmed
  → next_step

self_checking 未通过：
  → retrying(1..5)
  → 仍失败：blocked_for_human_review

人工未确认掌握：
  → remediate
  → 重新生成或补充练习
```

### 6.4 11 步步骤定义

| 步骤 | 目标 | 必交付物 | 人工确认标准 |
|---|---|---|---|
| 1. 动态专家 STORM 拆解 | 根据学习对象动态组建专家视角，穷举问题树 | 问题树、视角清单、学习范围 | 能说明为什么选择这些专家视角 |

| L4 分析 | 能拆解冲突、影响与风险 | 影响分析报告 | 覆盖主流程、异常流与依赖 |
| L5 创造 | 能设计新方案并论证取舍 | 新需求方案或 SOP | 通过毒舌测试与同行评审 |

## 7. 质量与治理规则

### 7.1 页面状态

| 状态 | 含义 | AI 消费策略 |
|---|---|---|
| `draft` | AI 起草或人工未确认 | 仅学习、评审、治理场景可读 |
| `confirmed` | Owner 已确认 | 生成与问答优先消费 |
| `conflict` | 存在未解决冲突 | 必须读取证据层并提示风险 |
| `superseded` | 已被新版本替代 | 默认不消费，仅演进追溯 |
| `deprecated` | 已废弃 | 默认不消费，仅历史研究 |

### 7.2 可信度评级

| 等级 | 判定 | 使用规则 |
|---|---|---|
| high | 多来源一致，Owner 确认，来源可回跳 | 可直接作为生成与问答依据 |
| medium | 单来源或存在少量模糊定义 | 输出时标记假设并提示复核 |
| low | 证据冲突、来源缺失或过期 | 不得直接输出结论 |

### 7.3 引用规则

所有 AI 生成内容必须携带：

1. 结论；
2. 引用页面；
3. `compiled_from` 或 KO；
4. 原文定位；
5. 版本与生效日期；
6. 不确定点。

## 8. 与现有系统的集成

### 8.1 与 KO 模型的关系

```text
KnowledgeObject
  ├─ raw_chunk / tables → 检索与证据溯源
  ├─ normalized → 页面正文的条目化知识
  ├─ wiki_page → Wiki 知识本体
  ├─ metadata → front-matter 与权限过滤
  └─ lineage → 来源、演进与引用定位
```

### 8.2 与 MCP 工具的关系

建议暴露三个分层工具：

| 工具 | 输入 | 输出 | 用途 |
|---|---|---|---|
| `get_wiki_manifest` | product_line | L0 manifest | 初始化与权限校验 |
| `get_domain_context` | product_line, domain | L2 摘要包 | 低成本生成与问答 |
| `read_wiki_pages` | page_ids, reason | L3 页面 | 精确边界、例外与演进 |

原有 `search_requirements` 保持不变，但内部策略改为：

```text
confirmed Wiki 域上下文包优先
  → 命中则返回 L2 + 必要 L3
  → 未命中则回落 RAG 混合检索
  → 记录命中与缺口，回流编译候选队列
```

## 9. 最小落地清单

第一阶段只需完成以下内容：

1. 建立一个产品线 Wiki 空间；
2. 编写 `_agent-manifest.yaml`、空间 `_index.md`；
3. 选择 1 个高频业务域，例如订单退款；
4. 编写 `_index.md`、`_domain-context.md`；
5. 编写 5 个术语页、10 个规则页、3 个流程页、5 个需求页；
6. 打通 `compiled_from` 到 KO 与原文定位；
7. 上线确认、冲突、废弃三种状态治理；
8. 上线一条 11 步学习路径，先跑退款需求攻坚；
9. 用 20 个真实问题对比“仅 RAG”与“Wiki 优先 + RAG 兜底”的答案质量。

## 10. 验收标准

| 维度 | 指标 |
|---|---|
| 渐进披露 | 常规生成任务默认读取 L0-L2；只有需要边界与证据时进入 L3-L4 |
| 上下文效率 | 单次生成任务注入的正文页面不超过 8 个 |
| 知识可信 | confirmed 页面 100% 有 owner、来源、生效日期、版本 |
| 溯源 | 关键结论可回跳到 KO 与原文定位 |
| 交互学习 | 每一步均通过自检、最多 5 次重试、人工确认后才跳转 |
| 实战闭环 | 每条学习路径至少产出需求片段、流程图、验收标准、配置或代码、截图 |
| 长效记忆 | 每条路径沉淀 15 张闪卡和复习计划 |
| 质量提升 | Wiki 优先策略在试点评测集上的答对率不低于纯 RAG 基线 |
