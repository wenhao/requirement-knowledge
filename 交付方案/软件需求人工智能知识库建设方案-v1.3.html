01

建设背景与目标

Background & Goals

1.1 背景

（1）内部现状：需求资产在沉睡

需求是软件工程的源头，也是缺陷修复成本最低的干预点——需求阶段的问题拖到上线后修复，成本呈数量级放大。公司多年积累的需求资产（PRD/MRD/SRS/评审纪要/变更记录）散落在各种格式的文档里，三个痛点长期存在：

复用难

新需求编写时找不到历史同类需求，"重造轮子"与"逻辑冲突"并存。

口径乱

同一业务概念在不同文档中定义不一致，跨团队沟通依赖"老员工脑子里的知识"。

知识流失

业务逻辑沉淀在个人经验而非组织资产中，人员流动即知识断层。

（2）需求知识库是 AI 软件工程（AI4SE）的上下文底座

AI 软件工程的落地正从下游向上游延伸：代码生成（最成熟）→ 测试生成 → 需求工程（最不成熟、杠杆最大）。通用大模型写代码已经可用，但让它写需求，产出的是"正确而通用"的模板文档——缺的不是模型能力，而是公司的私有上下文：业务规则、术语口径、历史决策与演进逻辑。

作用机制说明
上下文注入RAG 检索AI 生成需求时实时检索历史同类需求与业务规则注入生成上下文，让产出"有据可依"——最直接的作用
知识复利Wiki 式编译沉淀把散落文档增量编译为结构化、可维护的知识条目，知识从"文档堆"变为"活资产"，越用越准、越查越全
质量守护一致性校验生成结果对照库内规则与逻辑做冲突检测（B1 场景），AI 产出质量有了"参照系"
全流程贯通统一知识源打通需求→开发→测试的知识流（开发查背景、测试对照验收标准），AI 辅助从单环节扩展到软件工程全流程

一句话：没有需求知识库，AI 在需求工程环节就是"无米之炊"——模型决定下限，知识库决定上限。

（3）行业经验：成败在数据治理与运营，不在模型

这一判断有硬数据支撑：企业 AI 项目失败率约 80%（RAND），95% 的生成式 AI 试点无财务影响（MIT NANDA），失败归因高度一致地指向数据未治理与运营缺位，而非模型不够强。调研报告的失败案例库反复出现同一批根因：元数据缺失、新旧版本混存、上线后无人维护。因此本方案将建设重心放在知识资产的治理与运营机制上，模型选型退居其次。

1.2 使用场景全景（目标的需求来源）

建设目标从使用场景推导。按"需求工程生命周期 × 角色"框架对使用场景做穷举（详见第二章场景全景地图，共 8 组 20 个场景）：需求获取 → 编写生成 → 评审 → 变更 → 交付（开发/测试）→ 运营咨询 → 新人培训 → 知识治理，覆盖需求/产品/业务、开发/测试、客服/运营、新人、知识 Owner 五类角色。交互形态覆盖AI 生成检索（机器消费）、人机问答（对话交互）、知识运营面板（桌面需求 Agent 内嵌）三类（触点决策见 3.1.1）——前两类是 AI 知识库的本体能力，第三类保障知识资产持续可用。

1.4 设计原则（源自调研报告核心结论）

范式原则：RAG 与 Wiki 双范式一体——RAG 为主体、Wiki 为增强，且 Wiki 的分量随阶段递增

知识库当前有两种基本形式：检索式 RAG（原文分块入库，检索时即时召回）与生成式 Wiki（把文档编译为结构化知识页沉淀下来）。本方案不二选一，而是分阶段组合：

  • RAG 解决"从海量原文中找答案"：需求知识库规模天然超过长上下文极限（>2M token，共识 C8），且原文引用溯源是企业刚需（共识 C3）——RAG 是不可替代的主体，先建 RAG，最快形成价值。
  • Wiki 解决"知识越用越结构化"：高频被检索的需求域，把 RAG 命中的原文增量编译为术语表、业务规则页、需求演进页（AI 起草 + 知识 Owner 确认），沉淀为"活的知识资产"。调研报告观察到明确的融合趋势（T2 双范式融合："检索找答案、编译沉淀知识"），产品端 WeKnora 等已实现问答/Agent/Wiki 三模式共享同一知识库。
  • Wiki 的分量正在变重：通用大模型能力平权后，私有知识的结构化程度成为差异化的关键变量；组织级知识以 Wiki 形态沉淀后，既是人直接浏览的知识页，也是 AI 生成的高质量上下文（优先于原文命中）。但全量 LLM Wiki 在企业级并发编辑/权限/冲突消解上尚无成熟公开实践（调研空白 G2），故采用"按需增量编译"而非一步到位。

工程原则（六条，与范式原则同构：先有可信数据 → 再做可靠检索 → 然后放心编译 → 全程度量护航）

① 数据先行，元数据是召回的一半

清洗约占 40% 工作量；元数据不是锦上添花而是检索过滤的前提——缺元数据的知识库"语义都对、业务全错"（共识 C2，法律 RAG 失败案例根因）。

② 检索分层，简单问题不付 Agentic 成本

混合检索+重排覆盖 70-80% 事实型流量；只有多跳/关系型问题才升级 Agentic 路由（C1/C5）——RAG 管线先跑通，智能体按需加壳。

③ 编译守门，Wiki 只沉淀"确认过的知识"

知识页走"AI 起草 → Owner 确认 → 来源可审计"的人在回路（与 ADR-2 一致）；未确认内容不进优先检索层——Wiki 的价值在可信，不在量。

④ 引用溯源是硬指标

无论 RAG 答案还是 Wiki 页面，无出处不算数——RAG 附原文定位（C3），Wiki 附 compiled_from 来源链，两条范式同一把尺子。

⑤ 评测驱动，改什么都先跑回归

50-500 条真实评测集 + 反馈回流是分水岭（C4）；分块、嵌入、提示词、Wiki 编译规则的任何变更都先过评测再发布。

⑥ 工程务实：基建复用 + 生命周期检查

已有 PG → pgvector，不为"向量"引入新组件（C11）；选型查最近提交——h2oGPT/Verba 等已归档，GraphRAG/STORM 放缓（C12）。

  content:                          # 内容层（RAG 范式）
    raw_chunk: text                 # 原文分块（保留标题层级路径）→ 检索与引用
    normalized: text                # 条目化重写 → AI 需求生成消费（生成式增强）
    tables: [Table]                 # 业务规则表整块保留，不拆分
  wiki_page:                        # 知识页层（Wiki 范式，按需增量编译）
    page_id                         # 所属知识页（域内页面：术语-/规则-/需求-/FAQ- 前缀）
    compiled                        # AI 起草 + Owner 确认的结构化知识内容
    compiled_from                   # 编译来源 KO（可审计回溯）
    review_status                   # draft / confirmed（确认后才可被优先检索）
  metadata:                         # 元数据五要素 —— 精准召回的前提
    product_line / module / requirement_id
    version / status(active|deprecated|draft)
    effective_date / owner / confidentiality
  lineage:                          # 溯源层
    chunk_locator                   # 原文定位（文档名+页码/章节锚点）→ 引用硬指标
    related_kos                     # 需求演进链：v1 → v2 → 废弃（答新不答旧）
设计要点：三层内容——raw_chunk 服务检索与溯源，normalized 条目化内容服务 AI 需求生成，wiki_page 是 RAG 用出来的结构化沉淀（高频命中域从"原文"升级为"确认过的知识页"）；编译可审计——AI 起草内容必须经知识 Owner 确认（review_status 门控）且保留来源追溯链，人在回路、增量编译，规避全量 LLM Wiki 的企业化风险（调研空白 G2）。

2.2.1 KO 实例：一条退款规则如何变成知识对象

以一条真实需求片段为例（《XX商城退款需求规格说明书 v2.3.docx》第 5.2 节，2026-08 生效），看 KO 各层"是什么、为什么"：

  compiled_from: [KO-08712, KO-08715]   # 汇编两份文档同类规则，可审计回溯

  owner: 李四 / confidentiality: 内部

  related_kos: [KO-06210]        # v2.0 旧规则（已 superseded，检索默认过滤）
场景提问KO 里哪个字段在起作用
D2："REQ-2024-0871 说了什么？"requirement_id + raw_chunk → 按编号直达原文

H3/E1：沉淀退款规则知识页wiki_page.compiled → 确认后的知识页优先检索，人也可直接浏览

4.4 父子分块策略

小块 child（200-400 字）

向量召回定位：一个需求条目、一条业务规则、一个章节小节。

大块 parent（800-1500 字）

上下文供给：完整需求（背景+逻辑+验收标准）或完整章节，保证语义完整。

检索时小块命中 → 回溯取大块（+ 关联表格）进入生成上下文；标题层级路径作 chunk 前缀（"产品X › 订单模块 › 退款规则 › 3.2 超时处理"），提升定位与引用可读性。

4.5 元数据登记与增量更新

  • LLM 抽取 + 人工确认：解析后 LLM 抽元数据草案，运营面板人工确认后方可 active——"答新不答旧"与权限过滤的根基。
  • 单文档更新 = 新版本解析 → 新 chunk 入库 → 旧 chunk 标记 superseded（不物理删除，保留溯源回滚）→ 增量索引，勿整库重建。
  • 工具同步：JIRA/禅道需求状态变更自动回流 KO.status。
  • 过期检测：effective_date 超期未续期 → 自动降级，问答降权并提示"该知识可能过期"。

  • 每域一个 _index.md 域首页：本域知识地图，既是人的导航入口，也是 AI"域上下文包"的索引起点。
  • 演进内嵌：变更历史以时间线内嵌需求页；变更超 5 次才拆独立演进页（E1 默认读页内时间线）。
  • 术语两级：公司级口径归 90-全局，域内术语归域内——归属判定本身就是口径治理动作。
  • 命名规范：{类型前缀}-{名称}.md，同域页面按名称排序天然按类型分组。

（5）Wiki 用于需求生成：与 MCP+RAG 的对比与融合

Wiki 能否服务 A1 历史参考检索？能，且在高质量域上优于纯 MCP+RAG，但两者不是二选一：

维度MCP+RAG（检索原文 chunk）Wiki 知识页（确认过的结构化知识）
内容质量原文片段，质量随文档参差Owner 确认过的知识，噪声低、口径统一
完整性chunk 碎片，需拼装一个域/一条规则的完整知识单元
token 效率多 chunk 组上下文，冗余高域首页+规则页即"域上下文包"，密度高
时效性入库即可检索，零冷启动需编译+确认，滞后 1-4 周
覆盖面全量文档域仅 Top 高频域（编译覆盖率有限）
演进一致性靠元数据过滤，仍有混入风险页面即现行版（编译时已消解版本）

结论（写入 A1 检索策略）：分层检索——Wiki 优先、RAG 兜底

A1 生成检索请求 search_requirements(product, module, intent)
  ① 命中 confirmed 知识页？→ 返回域上下文包（_index + 相关规则/需求页）
     ——质量高、完整、token 省；随编译覆盖率扩大份额
  ② 未命中（长尾域/新需求域）→ 回落 RAG 管线（混合检索+重排）
     ——覆盖全量，零冷启动
  ③ 命中统计回流 Langfuse → 未命中频次高的域进入编译候选队列
     ——RAG 的使用驱动 Wiki 的生长（与编译触发条件闭环）

对生成质量的影响：写"预售退款"需求时，若退款域已有 confirmed 知识页，AI 拿到的是"术语定义+现行规则+例外清单+演进脉络"的完整域包，而非十几段原文碎片——生成需求与现行逻辑的一致性、术语准确度、验收标准完整度都更高。Wiki 份额随阶段递增的量化表达：P1 末 Wiki 命中占 A1 流量约 20%（首批编译域），P2 目标 40%+（覆盖 80% 高频域后）——纳入月度质量报告。
