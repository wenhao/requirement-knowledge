一、L1 需求 Spec：优惠券叠加规则

项 内容
作者 产品经理 张三
日期 2026-11-04
状态 已确认
关联知识库条目 术语-优惠券门槛 · 规则-退款金额分摊 · 决策-店铺券先于平台券

1.1 问题与目标

当前每单只允许使用一张优惠券，大促期间用户希望”店铺券 + 平台券”组合使用。运营侧每年因无法组合发券，需要设计大量单品专享券，配置成本高。

衡量指标：

  • 券核销率提升 ≥ 8%；
  • 因优惠配置导致的客服工单下降 ≥ 20%；
  • 优惠计算错误率为 0（资金红线）。

1.2 用户故事

  1. 作为买家，我希望下单时同时使用一张店铺券和一张平台券，以便获得最大优惠；
  2. 作为运营人员，我希望系统按固定优先级自动计算叠加结果，以便不必为每个组合单独建券；
  3. 作为财务人员，我希望退款时按实付金额比例分摊优惠，以便对账口径一致。

1.3 业务规则（每条可判定真假）

编号 规则 来源
R1 每单最多使用 1 张平台券 + 1 张店铺券 新增
R2 折扣券与折扣券不可叠加；满减券与满减券不可叠加 知识库：决策-叠加互斥
R3 优惠计算顺序：先店铺券，后平台券 知识库：决策-店铺券先于平台券
R4 叠加后单笔订单实付金额不得低于 0.01 元 新增
R5 退款按商品实付金额占比分摊优惠，分摊误差 ≤ 0.01 元且由尾差规则兜底 知识库：规则-退款金额分摊
R6 赠品、运费、保险费不计入优惠券使用门槛 知识库：术语-优惠券门槛
R7 虚拟商品与跨境订单本期不支持叠加用券 新增（非目标）
R8 券库存扣减与订单创建必须防超发（并发场景） 新增

1.4 边界与异常

类别 约定
输入边界 优惠券门槛金额按商品小计（税前、优惠前）计算；金额单位为分
并发与幂等 同一订单重复请求优惠试算/锁定接口，结果必须幂等；防超发用 Redis 原子扣减 + 数据库乐观锁兜底
权限 仅买家本人可为自己的订单用券；运营后台可配置模板，不可代客锁定
兼容性 旧版下单入口（App ≤ 5.8）不展示叠加入口，行为保持单券
异常流 券引擎超时或异常时，下单降级为”不可用券”并明确提示，不阻断下单
资金安全 所有金额用 Decimal（分为单位）计算，禁止浮点数；优惠流水全量落库可审计

1.5 验收标准（Given/When/Then）

编号 验收标准
AC1 Given 订单满足店铺券门槛，When 买家同时选择店铺券与平台券，Then 两个优惠按 R3 顺序生效且实付金额计算正确
AC2 Given 订单实付金额低于 0.01 元，When 叠加计算完成，Then 实付金额固定为 0.01 元且差额部分按 R3 逆向削减优惠
AC3 Given 买家选择两张平台券，When 提交订单，Then 系统拒绝并提示”每单最多使用一张平台券”
AC4 Given 商品含赠品与运费，When 计算用券门槛，Then 赠品与运费金额不计入门槛
AC5 Given 券库存仅剩 1 张，When 两个买家并发提交订单，Then 只有 1 单成功锁券，另一单明确失败
AC6 Given 使用叠加券的订单部分退款，When 执行退款，Then 每个商品按实付占比分摊优惠，误差 ≤ 0.01 元
AC7 Given 虚拟商品订单，When 进入结算页，Then 叠加用券入口置灰并提示”暂不支持”
AC8 Given 券引擎超时，When 买家提交订单，Then 订单可不用券正常创建并出现降级提示

1.6 非目标（本期明确不做）

  • 不做三张及以上优惠券叠加；
  • 不做积分抵扣与会员价参与叠加；
  • 不做优惠券转赠与分享；
  • 不改造旧版收银台 UI。

1.7 开放问题

问题 负责人 截止日期 状态
平台券与店铺券同门槛时谁先计算是否影响金额？ 开发 2026-11-06 已关闭（R3 固定顺序）
跨境订单后续是否放开？ 产品 2026-11-15 跟踪中（不阻塞本期）

二、L2 技术 Spec：优惠券叠加规则

2.1 方案概述与备选方案对比

新建独立的 coupon-engine 领域模块，以”规则表 + 计算管线”承载叠加逻辑；订单服务通过内部 API 调用，不侵入订单主流程。

备选方案 结论 理由
A：独立 coupon-engine 模块 采纳 规则集中、可独立测试与灰度；避免优惠逻辑散落订单代码
B：在订单服务内 if-else 实现 否决 规则会持续膨胀，跨模块耦合，后续无法独立演进
C：外采营销中台 暂缓 成本与排期不匹配，本期先沉淀内部规则模型

2.2 架构与模块改动

订单服务 order-service
   │ ①预览 / ②锁定 / ③核销 / ④回退
   ▼
优惠券引擎 coupon-engine（新增）
   ├─ rule-loader    加载 R1–R8 规则与券模板
   ├─ calculator     按顺序计算店铺券 → 平台券
   ├─ inventory      券库存原子扣减（Redis + DB 乐观锁）
   └─ refund-alloc   退款按实付占比分摊
   ▼
财务服务 finance-service（退款分摊流水回写）

涉及文件（示例）：

  • services/order/checkout.py：调用券预览与锁定；
  • services/coupon-engine/：新增模块；
  • services/finance/refund.py：接入分摊流水；
  • docs/specs/coupon-stacking/：本 Spec 与规则表入库。

2.3 数据模型与迁移

表 关键字段 说明
coupon_template id, type(满减/折扣), threshold, amount, scope 券模板，运营配置
user_coupon id, user_id, template_id, status, expire_at 用户持券状态
order_coupon_record order_id, coupon_id, deduct_amount, calc_snapshot 优惠流水，保存计算快照供审计
refund_allocation refund_id, order_id, item_id, alloc_amount 退款分摊明细

迁移策略：先建表并双写影子流量 3 天，对账一致后切换读路径；旧单券字段保留 90 天兼容期。

2.4 API 契约

接口 用途 关键约定
POST /internal/coupons/preview 结算页试算可用券与叠加结果 幂等键 order_draft_id；只读不扣库存
POST /internal/coupons/lock 下单锁定券与扣减库存 幂等键 order_id；失败返回明确错误码
POST /internal/coupons/settle 支付成功核销 幂等键 payment_id；写 order_coupon_record
POST /internal/coupons/rollback 超时/取消/全额退款回退 幂等键 order_id + seq；恢复库存

错误码示例：COUPON_SOLD_OUT（库存不足）、COUPON_THRESHOLD_NOT_MET（未达门槛）、COUPON_COMBINATION_REJECTED（组合违规）、COUPON_ENGINE_DEGRADED（引擎降级）。

2.5 异常处理与降级

  • 券引擎 P99 > 200ms 连续 10 次：熔断，结算页降级为不可用券并提示；
  • 降级期间下单不阻断，订单标记 coupon_degraded，事后再营销补偿；
  • 所有锁定操作带 15 分钟超时自动回退（T+0 定时任务）。

2.6 安全与合规

  • 金额全部以”分”为单位的 Decimal 运算，禁止 float；
  • 优惠流水 calc_snapshot 保存规则版本号与输入输出，满足审计追溯；
  • 接口仅限内网服务账号调用，操作日志保留 180 天；
  • 券库存扣减与订单创建跨表一致，采用”先锁券、后建单、失败回退”补偿。

2.7 测试策略

层级 范围 要求
单元测试 R1–R8 规则矩阵、金额计算、尾差分摊 覆盖率 ≥ 90%，规则用例 ≥ 60 个
集成测试 预览/锁定/核销/回退全链路 AC1–AC8 全部自动化
并发测试 AC5 库存超发场景 压测 1000 并发无超发
回归测试 旧版单券下单、退款对账 双写影子对账 3 天零差异
资损演练 降级、回退、幂等重放 演练记录入验收材料

2.8 灰度与回滚

  • 灰度开关 coupon_engine_v2 按 1% → 10% → 50% → 100% 流量放开；
  • 每个阶段观察核销率、资损告警、P99 延迟至少 24 小时；
  • 回滚预案：关闭开关即回到旧单券链路；已灰度订单按 calc_snapshot 继续履约，不受影响。

三、L3 任务拆解（每任务 ≤ 0.5–1 天）

任务 名称 前置 涉及文件 验收（可执行） 风险与回滚
T1 规则表与规则加载器 — coupon-engine/rule_loader.py R1–R8 规则以数据文件加载，单测全绿 规则文件版本化，可回退
T2 金额计算管线 T1 coupon-engine/calculator.py AC1、AC2 单测通过，金额 Decimal 计算器纯函数，无状态可替换
T3 预览接口 T2 coupon-engine/api/preview.py 幂等重放结果一致，P99 < 100ms 只读接口，直接下线
T4 库存锁定与防超发 T1 coupon-engine/inventory.py AC5 并发压测无超发 超时自动回退任务兜底
T5 订单服务接入 T3, T4 services/order/checkout.py 下单成功锁券，取消后回退 开关 coupon_engine_v2 控制
T6 退款分摊接入 T2 services/finance/refund.py AC6 分摊误差 ≤ 0.01 元 分摊流水可重放修正
T7 灰度开关与监控 T5 infra/flags, monitoring 资损告警、P99、核销率看板可用 关开关即回旧链路
T8 知识回写 T5, T6 需求知识库/营销域 R1–R8 与决策回写知识库并过产品审核 知识库版本化

四、试点使用说明

  1. 替换业务：将”优惠券叠加”替换为真实试点需求，保留本文件结构与评审顺序；
  2. 先评后写：先填第〇章六维就绪度评估表确认路由（高分 + 大规模 → B），再进入 L1/L2/L3；任一维 ≤ 2 时，先补齐对应短板（转 Markdown、补内容、补 Given/When/Then、补知识、补技术方案与指标、拆任务）再重评；
  3. 技术补充：L2 技术 Spec 由开发编写——技术方案与约束、技术/性能指标、边界条件、异常处理补齐后，才允许进入 AI Coding；
  4. 规则可判定：L1 的每条规则必须能回答”是/否”，做不到就回到需求澄清；
  5. 验收先行：AC1–AC8 必须在写代码前评审通过，并与自动化测试一一对应；
  6. 知识回写：T8 为强制任务，未回写知识库的需求不算交付完成；
  7. 度量挂钩：试点结束时对照主方案第六章指标采集数据（任务一次通过率、Spec 评审通过率、知识回写率）。
