# 软件需求 AI 知识库建设方案

> **方案定位**：公司内部建设"软件需求"领域的 AI 知识库，沉淀历史需求文档与业务逻辑，供 AI 辅助需求生成时检索历史需求及其逻辑、支撑业务逻辑问答检索等场景；需求文档格式多样（PDF、Office doc/docx 等），须支持便捷上传入库，并支持用户对知识进行日常调整与维护。本方案基于《AI 知识库建设方法与开源框架产品调研 v5（穷尽版）》的方法论与选型证据，直接引用其结论并映射到本场景。

## 一、建设背景与目标

### 1.1 背景

**（1）内部现状：需求资产在沉睡**

需求是软件工程的源头，也是缺陷修复成本最低的干预点——需求阶段的问题拖到上线后修复，成本呈数量级放大。公司多年积累的需求资产（PRD/MRD/SRS/评审纪要/变更记录）散落在各种格式的文档里，三个痛点长期存在：

- **复用难**：新需求编写时找不到历史同类需求，"重造轮子"与"逻辑冲突"并存；
- **口径乱**：同一业务概念在不同文档中定义不一致，跨团队沟通依赖"老员工脑子里的知识"；
- **知识流失**：业务逻辑沉淀在个人经验而非组织资产中，人员流动即知识断层。

**（2）需求知识库是 AI 软件工程（AI4SE）的上下文底座**

AI 软件工程的落地正从下游向上游延伸：代码生成（最成熟）→ 测试生成 → 需求工程（最不成熟、杠杆最大）。通用大模型写代码已经可用，但让它写需求，产出的是"正确而通用"的模板文档——缺的不是模型能力，而是**公司的私有上下文**：业务规则、术语口径、历史决策与演进逻辑。需求知识库对 AI4SE 的作用正在于此：

| 作用 | 机制 | 说明 |
|---|---|---|
| 上下文注入 | RAG 检索 | AI 生成需求时实时检索历史同类需求与业务规则注入生成上下文，让产出"有据可依"——最直接的作用 |
| 知识复利 | Wiki 式编译沉淀 | 把散落文档增量编译为结构化、可维护的知识条目，知识从"文档堆"变为"活资产"，越用越准、越查越全 |
| 质量守护 | 一致性校验 | 生成结果对照库内规则与逻辑做冲突检测（B1 场景），AI 产出质量有了"参照系" |
| 全流程贯通 | 统一知识源 | 打通需求→开发→测试的知识流（开发查背景、测试对照验收标准），AI 辅助从单环节扩展到软件工程全流程 |

一句话：**没有需求知识库，AI 在需求工程环节就是"无米之炊"——模型决定下限，知识库决定上限。**

**（3）行业经验：成败在数据治理与运营，不在模型**

这一判断有硬数据支撑：企业 AI 项目失败率约 80%（RAND），95% 的生成式 AI 试点无财务影响（MIT NANDA），失败归因高度一致地指向数据未治理与运营缺位，而非模型不够强。调研报告的失败案例库反复出现同一批根因：元数据缺失、新旧版本混存、上线后无人维护。因此本方案将建设重心放在知识资产的治理与运营机制上，模型选型退居其次。

### 1.2 使用场景全景（目标的需求来源）

建设目标从使用场景推导。按"需求工程生命周期 × 角色框架"对使用场景做穷举（详见 2.1 场景全景地图，共 8 组 20 个场景）：需求获取 → 编写生成 → 评审 → 变更 → 交付（开发/测试）→ 运营咨询 → 新人培训 → 知识治理，覆盖需求/产品/业务、开发/测试、客服/运营、新人、知识 Owner 五类角色；交互形态覆盖 AI 生成检索（机器消费）、人机问答（对话交互）、知识运营面板（桌面需求 Agent 内嵌）三类（触点决策见 3.1.1），前两类是 AI 知识库的本体能力，第三类保障知识资产持续可用。

从 20 个场景归纳为四条主线目标，每条目标绑定服务场景与可验收指标；变更追溯、冲突检测、精确查询、影响分析等能力指标（原 G6-G9）作为主线目标在各阶段验收项中体现，不单列。

| # | 目标 | 服务场景 | 衡量口径（验收指标） |
|---|---|---|---|
| G1 需求生成智能化 | AI 辅助需求生成时检索历史需求及逻辑，支撑复用、相似检测与冲突预警 | SC-A/B 组 | 生成入口集成检索 API，历史需求片段召回 Hit@3 ≥ 80%；演进链覆盖率 ≥ 90%（P1）；相似/冲突检出（人工标注集）召回 ≥ 60%（P2 上线门槛） |
| G2 业务逻辑可溯源问答 | 业务逻辑、术语口径、规则明细、变更影响的可溯源问答 | SC-C/D/E/F/G 组 | 答案 100% 附原文引用，引用正确率 ≥ 90%；编号/字段类查询 top-5 准确率 ≥ 90%；拒答正确率 ≥ 95%（幻觉治理） |
| G3 知识资产化 | 多格式文档便捷入库，知识条目化沉淀为可维护的活资产 | SC-H 组 | PDF/doc/docx/扫描件一键上传，解析成功率 ≥ 95%，入库 SLA ≤ 10 分钟；术语表/FAQ 沉淀机制运转（P2） |

### 1.4 设计原则（源自调研报告核心结论）

**范式原则：RAG 与 Wiki 双范式一体，RAG 为主体、Wiki 为增强，且 Wiki 的分量随阶段递增**

知识库当前有两种基本形式：检索式 RAG（原文分块入库，检索时即时召回）与生成式 Wiki（把文档编译为结构化知识页沉淀下来）。本方案不二选一，而是分阶段组合：

- **RAG 解决"从海量原文中找答案"**：需求知识库规模天然超过长上下文极限（>2M token 决策树结论，共识 C8），且原文引用溯源是企业刚需（共识 C3）——RAG 是不可替代的主体，先建 RAG，最快形成价值。
- **Wiki 解决"知识越用越结构化"**：高频被检索的需求域，把 RAG 命中的原文增量编译为术语表、业务规则页、需求演进页（AI 起草 + 知识 Owner 确认），沉淀为"活的知识资产"。调研报告观察到明确的融合趋势（T2：双范式融合，RAG 与生成式知识编译互为补充——"检索找答案、编译沉淀知识"），且产品端 WeKnora 等已实现问答/Agent/Wiki 三模式共享同一知识库。
- **Wiki 的分量正在变重**：通用大模型能力平权后，私有知识的结构化程度成为差异化的关键变量；组织级知识（术语口径、业务规则、演进脉络）以 Wiki 形态沉淀后，既是人直接浏览的知识页，也是 AI 生成的高质量上下文（优先于原文命中）。但全量 LLM Wiki 在企业级并发编辑/权限/冲突消解上尚无成熟公开实践（调研空白 G2），故采用"按需增量编译"而非一步到位。

**工程原则（六条，与范式原则同构：先有可信数据 → 再做可靠检索 → 然后放心编译 → 全程度量护航）**

1. **数据先行，元数据是召回的一半**：数据清洗约占 40% 工作量；元数据（版本/生效日期/产品线/部门）不是锦上添花而是检索过滤的前提——缺元数据的知识库"语义都对、业务全错"（共识 C2，法律 RAG 失败案例根因即元数据缺失）。
2. **检索分层，简单问题不付 Agentic 成本**：混合检索（BM25+向量+RRF）+ cross-encoder 重排覆盖 70-80% 的事实型流量；只有多跳/关系型问题才升级 Agentic 检索路由（共识 C1、C5）——检索架构与范式原则同构：RAG 管线先跑通，智能体增强按需加壳。
3. **编译守门，Wiki 只沉淀"确认过的知识"**：知识页编译走"AI 起草 → Owner 确认 → 来源可审计"的人在回路（与 ADR-2 一致）；未经确认的 AI 生成内容不进入优先检索层——Wiki 的价值在可信，不在量。
4. **引用溯源是硬指标**：无论 RAG 答案还是 Wiki 知识页，无出处不算数——RAG 答案附原文定位（共识 C3），Wiki 页面附 compiled_from 来源链，两条范式同一把尺子。
5. **评测驱动，改什么都先跑回归**：50-500 条真实业务问题评测集 + 反馈回流，是知识库从 demo 变产品的分水岭（共识 C4）；分块、嵌入、提示词、Wiki 编译规则的任何变更都先过评测再发布。
6. **工程务实：基建复用 + 组件生命周期检查**：已有 PostgreSQL → pgvector(+pgvectorscale)，已有 ES → kNN，不为"向量"引入新组件（共识 C11）；选型前查仓库最近提交与归档状态——h2oGPT/Verba/Reor/Vanna 已归档，Microsoft GraphRAG/STORM 维护放缓（共识 C12）。

## 二、场景分析与需求定义

#### 场景 × 优先级统计与架构含义

| 优先级 | 场景数 | 阶段 |
|---|---|---|
| P0 | 7（A1、C1、D1、D2、G1、H1、H2） | MVP（W3-8） |
| P1 | 7（A2、C2、C3、E1、F1、G2、G3） | 增强（W9-16） |
| P2 | 6（A3、B1、B2、E2、F2、H3；其中 B1、F2 依赖图谱能力） | 深化（W17-26） |
| P3 | 版图外（4 项候选） | 扩展评估 |

架构含义汇总：
- **机器消费 vs 人机问答 vs 知识运营面板**三类交互形态并存 → 知识库以 MCP 工具服务 Web 需求生成、以问答服务桌面需求 Agent 与 IM 机器人、以面板承载知识运营（复用已有触点，见 3.1.1 触点决策）。
- **多跳/关系型场景**（A3、B1、B2、C3、F1、F2）集中 P1-P2 → 印证 ADR-5：GraphRAG 延后到阶段二按数据决策。
- **版本/演进类场景**（E1、E2）与**精确查询类场景**（D1、D2、C2、G3）→ 印证元数据五要素与 BM25 混合检索为必选项。
- **治理场景**（H1-H3）全程 P0/P2 → 知识库"活过 90 天"依赖治理场景与消费场景同权重投入。

### 2.2 核心知识对象模型

统一知识对象（KO，Knowledge Object）是全部 20 个场景共用的底座：

```yaml
KnowledgeObject:
  ko_id: string              # 唯一标识
  source_doc:                # 源文档信息
    doc_id, filename, format(pdf/docx/...), uploader, upload_time
  content:                   # 内容层（RAG 范式）
    raw_chunk: text          # 原文分块（保留标题层级路径）
    normalized: text         # 结构化重写（SC-A 生成检索场景消费，需求条目化）
    tables: [Table]          # 表格整块保留（业务规则表）
  wiki_page:                 # 知识页层（Wiki 范式，按需增量编译）
    page_id: string          # 所属知识页（域内页面：术语-/规则-/需求-/FAQ- 前缀）
    compiled: text           # AI 起草+Owner 确认的结构化知识内容
    compiled_from: [ko_id]   # 编译来源（可审计回溯）
    review_status: enum      # draft / confirmed（确认后才可被优先检索）
  metadata:                  # 元数据层（精准召回的前提，共识 C2）
    product_line: string     # 产品线（如：交易/履约/会员）
    module: string           # 功能模块
    requirement_id: string   # 关联需求编号（如 JIRA/禅道 ID）
    version: string          # 需求版本 / 文档版本
    status: enum             # active / deprecated / draft
    effective_date: date     # 生效日期（答新不答旧的关键）
    owner: string            # 责任人（知识确权）
    confidentiality: enum    # 密级（公开/内部/保密）→ 权限过滤依据
  lineage:                   # 溯源层（引用硬指标，共识 C3）
    chunk_locator: string    # 原文定位（文档名+页码/章节锚点）
    related_kos: [ko_id]     # 关联知识（需求演进链：v1→v2→废弃）
```

要点：
- **三层内容设计**：raw_chunk 服务检索与引用溯源；normalized 条目化内容服务 AI 需求生成（机器消费）；wiki_page 是 RAG 用出来的结构化沉淀——高频命中域从"原文"升级为"确认过的知识页"，实现"检索找答案、编译沉淀知识"的双范式闭环。
- **编译可审计**：wiki_page.compiled_from 保留来源 KO 追溯链，AI 起草内容必须经知识 Owner 确认（review_status=confirmed）才可被优先检索——吸收生成式范式（把原文编译为结构化知识）的优点，但以增量、可审计、人在回路的方式实现。
- **元数据五要素**（product_line / version / status / effective_date / owner）直接决定 A1 生成检索、C1 问答等核心场景的召回精度，是数据治理的核心字段。
- **需求演进链**（related_kos）解决"新旧版本混存答旧不答新"问题：新版本标记旧条目为 superseded，检索层默认过滤。

### 2.2.1 KO 实例：一条退款规则如何变成知识对象

以一条真实需求片段为例，看 KO 各层"是什么、为什么"：

> 源文档：《XX商城退款需求规格说明书 v2.3.docx》第 5.2 节（2026-08 生效）

```yaml
ko_id: KO-08712
source_doc: { doc_id: D-1024, filename: XX商城退款需求规格说明书v2.3.docx, format: docx, uploader: 张三, upload_time: 2026-08-02 }
content:
  raw_chunk: |
    5.2 退款超时处理
    订单支付成功后 48 小时内未发货的，系统自动发起全额退款；
    退款金额 T+1 个工作日原路退回；虚拟商品不适用本规则……
    （标题路径前缀：XX商城 > 订单模块 > 退款规则 > 5.2 超时处理）
  normalized: |
    【规则】退款超时自动退款
    触发条件：订单支付成功且 48 小时未发货
    动作：全额退款，T+1 工作日原路退回
    例外：虚拟商品不适用
  tables: [表5-2 各支付渠道退款时效]      # 渠道规则表整块挂载
wiki_page:
  page_id: 10-订单/规则-退款超时           # 归入订单域的规则页（域目录/类型前缀命名）
  compiled: "退款超时=支付后48h未发货→自动全额退款（虚拟商品除外）"
  compiled_from: [KO-08712, KO-08715]    # 汇编了两份文档中的同类规则
  review_status: confirmed               # 知识 Owner 已确认
metadata:
  product_line: 商城 / module: 订单-退款
  requirement_id: REQ-2024-0871          # 关联 JIRA 需求号 → D2 场景按编号直达
  version: v2.3 / status: active / effective_date: 2026-08-01
  owner: 李四 / confidentiality: 内部
lineage:
  chunk_locator: XX商城退款SRS v2.3 · 5.2 节 · 第 41 页   # 答案引用点这里回跳原文
  related_kos: [KO-06210]                # v2.0 的旧规则（已标 superseded，检索默认过滤）
```

**这个结构解决什么问题**——对着 20 个场景看：

| 场景提问 | KO 里哪个字段在起作用 |
|---|---|
| D2："REQ-2024-0871 说了什么？" | `requirement_id` + raw_chunk → 按编号直达原文 |
| C2："退款超时怎么处理？" | raw_chunk + tables → 表格整块命中，规则不断裂 |
| C1："现行退款逻辑是什么？"（多版本并存） | `status`/`effective_date` → 答 v2.3 不答 v2.0（related_kos 标记旧版） |
| A1：AI 写"预售退款"需求时找参考 | `metadata`（产品线/模块过滤）+ normalized → 注入生成上下文的是条目化规则而非散文段落 |
| H3/E1：沉淀退款规则知识页 | `wiki_page.compiled` → 确认后的知识页优先检索，人也可直接浏览 |
| 权限：实习生不该看保密产品线 | `confidentiality` → 检索层过滤，结果根本不出现在候选里 |

一句话：**KO 把"一段需求文字"升级为"带身份（元数据）、带历史（演进链）、带出处（定位）、带两种消费形态（原文/条目）的知识资产"——20 个场景都是对这份资产不同角度的取用。**

### 2.3 非功能性需求

| 维度 | 要求 |
|---|---|
| 权限 | 按部门/产品线隔离；密级过滤在**检索层**执行而非应用层（欧盟 AI Act 合规基线，共识 C2） |
| 私有化 | 需求资产涉密，全栈私有化部署，数据不出域；模型可选内网推理或合规云 API |

| 规模 | 首期按 5,000-50,000 份文档、百万级 chunk 设计，架构上亿级向量可扩展 |

### 3.1.1 用户触点与入口决策

公司已有两个用户触点，知识库**复用触点而非新建门户**：

| 触点 | 形态 | 承载场景 | 接入方式 | 建设策略 |
|---|---|---|---|---|
| **Web 端 AI 需求生成**（已有） | Web 应用 | SC-A 组：生成检索（A1/A2/A3），生成结果附知识库引用 | MCP 工具 / REST API | 复用：后端接入检索服务即可，前端仅加"引用来源"展示 |
| **桌面端需求 Agent**（已有，主入口） | 桌面客户端 | SC-C/D/E/F/G 组：问答与检索；SC-H 组：知识运营 | MCP/REST API + **内嵌知识库可视化运营面板** | 复用+增强：面板为本方案二开项（11.6），在 Agent 内直接运营知识 |
| IM 机器人（新增，轻量辅助） | 企微/飞书机器人 | SC-C/D 组轻量问答（客服、业务方等免装桌面端用户） | WeKnora 原生直连企微/飞书 | 近零成本开通，作为兜底入口 |

两项明确不做：

- **不自建独立 Web 问答台**：问答主场景由桌面需求 Agent 承载，低频/轻量用户由 IM 机器人覆盖——三套问答入口会分散用户与运营精力，且 WeKnora Web 端仅作 UAT 验收与知识 Owner 管理后台使用，不对全员开放。
- **不采用 WeKnora 独立桌面端**：与公司桌面需求 Agent 定位重叠，无独立使用场景；WeKnora 仅作为服务端底座（Docker/K8s 部署），通过 API/MCP 供各触点消费。

**知识库可视化运营面板**（桌面需求 Agent 内嵌；早期版本称"知识台"，v1.3 起统一为 Agent 内嵌面板）：

| 面板区块 | 功能 | 对应场景 |
|---|---|---|
| 知识浏览 | Wiki 知识页（术语/规则/演进）浏览与搜索；需求文档库导航 | H3、全员浏览 |
| 上传入库 | 拖拽上传（pdf/doc/docx/扫描件）、解析预览、失败重试 | H1 |
| 元数据确认 | LLM 抽取五要素草案的确认/修正工作流；演进链登记 | H1/H2 |
| 条目管理 | normalized 条目编辑、状态标记（active/deprecated/draft）、合并重复 | H2 |
| Wiki 编译确认 | AI 起草知识页的审阅/驳回/发布（ADR-2 门控） | H3 |
| 反馈队列 | "点不对"归因处理（检索错/生成错/数据错分流） | H2 |
| 质量看板 | 命中率、引用率、拒答率、过期知识占比、Wiki 反哺对比（Langfuse 数据源） | H2/运营 |

### 3.2 架构决策记录（ADR 摘要）

| # | 决策 | 理由（调研报告证据） |
|---|---|---|
| ADR-1 | **RAG 为主体、Wiki 为增强的双范式一体**：先建 RAG（原文检索+溯源），高频命中域增量编译为知识页（wiki_page），Wiki 分量随阶段递增 | 需求知识库规模 >2M token 且需版本/权限/审计治理 → RAG 是不可替代的主体（决策树结论 + 共识 C7/C8）；知识结构化沉淀决定长期差异化 → Wiki 增强必要（T2 双范式融合趋势）；但全量 LLM Wiki 缺企业级并发编辑/权限/冲突消解实践（空白 G2）→ 只做增量编译 |
| ADR-2 | Wiki 编译走"AI 起草 + Owner 确认 + 来源可审计"的人在回路，confirmed 知识页在检索中优先于原文 | 组织知识的可信度要求高于生成自由度；compiled_from 追溯链 + review_status 门控保证可审计；"检索找答案、编译沉淀知识"形成闭环 |
| ADR-3 | 向量库选 pgvector 复用 PG，不引入独立向量库 | 共识 C11：向量库已商品化，已有 PG 基建优先 pgvector；纯向量库窗口关闭 |
| ADR-4 | 知识库以 MCP server 形态对需求生成 Agent 暴露 | 共识 C9：MCP 是知识库暴露给 Agent 的事实标准（Outline/Wren AI/OpenViking/Mem0 全线支持） |
| ADR-5 | GraphRAG 延后到阶段二按需引入 | 共识 C6：索引成本 10-50 倍于向量；需求"功能依赖/规则冲突"类关系型问题占比实测超阈值后再上 |
| ADR-6 | 权限过滤在检索层执行 | 法律 RAG 失败案例 + 欧盟 AI Act 合规基线（共识 C2） |
| ADR-7 | 引用溯源为硬性验收指标 | 共识 C3：无出处的答案不算数 |

## 四、数据治理与文档处理管线

> 调研报告定量证据：数据清洗约占项目工作量 40%；"50 份核心文档结构化解析与元数据登记，比换更强模型收益更大"。

### 4.1 知识源盘点（第一步，决定成败）

| 知识源 | 典型形态 | 优先级 | 说明 |
|---|---|---|---|
| 需求规格说明书 SRS/PRD | docx/pdf，章节层级深 | P0 | 核心资产，首期入库 |
| 需求评审/澄清纪要 | docx/在线文档导出 | P0 | 含决策逻辑（为什么这么做） |
| 需求变更记录 | 工单系统导出/表格 | P0 | 构建演进链（v1→v2→废弃） |
| 业务规则/流程文档 | pdf + 流程图 | P0 | C1/C2 业务逻辑问答主体 |
| 原型/接口文档 | 图片/pdf/在线 | P1 | 原型图入库需图像处理能力，阶段二 |
| 历史需求条目库 | JIRA/禅道导出 | P1 | 结构化程度高，抽取即用 |
| 会议录音转写 | 文本 | P2 | 质量参差，后置 |

盘点时同步登记：版本、责任人、密级、所属产品线——即 KO 元数据五要素的原始登记。

### 4.2 深度解析（针对多格式输入，H1 场景核心）

**格式路由**：
- **docx**：结构保留最好，直取标题层级+段落+表格（pandoc/mammoth 类方案或解析器直处理）。
- **PDF（文本型）**：版面解析还原阅读顺序与标题层级（MinerU/Docling/DeepDoc）。
- **PDF（扫描件）/图片**：OCR（PaddleOCR/PP-StructureV3 中文底座）+ 人工抽检校对。
- **表格密集文档**：表格专项解析（PP-StructureV3/Table Transformer），**整块保留不拆分**。

**解析选型建议**（调研报告 3.5 节组件速查）：
- 开箱开源首选 **MinerU**（82.7k★，PDF/Office→Markdown/JSON，注意 AGPL 商用许可复核）或 **Docling**（海外主流、许可更宽松）。
- 平台级方案：若选 RAGFlow 平台，其 **DeepDoc** 内置版面解析，合同/手册/报表级复杂文档能力强。
- 商用 API 备选：TextIn xParse（¥0.042/页，99.7% 识别率）、阿里文档智能（¥0.02-0.04/页）——扫描件量大或解析质量不达标时切换。
- 视觉密集文档（原型图密集页）：阶段二可评估 ColPali/ColQwen 免 OCR 路线（注意每页约 1030 向量的存储成本）。

**高频陷阱与对策**（调研报告失败案例库）：

| 陷阱 | 后果 | 对策 |
|---|---|---|
| 300 页 PDF 不切分直接入库 | 命中率极差 | 版面解析 + 语义分块强制执行 |
| 512 token 定长切片 | "不保本"类风险警示被拦腰截断 | 语义段落切块（300-500 字），标题层级保留；金融案例教训 |
| 表格按行拆分 | 业务规则表逻辑断裂 | 表格整块保留，单元格关系不破坏 |
| 新旧版本混存 | 答旧不答新（银行 2019 利率案例） | 演进链标记 + status/effective_date 过滤 |
| 嵌入不含结构元数据 | 法律 RAG 失败案例根因：语义相似但业务上不适用 | 元数据登记为入库必经步骤，LLM 抽取+人工确认 |

### 4.3 分块策略（父子分块）

- **小块（child，200-400 字）**：用于向量召回定位——一个需求条目、一条业务规则、一个章节小节。
- **大块（parent，800-1500 字）**：用于上下文供给——完整需求描述（背景+逻辑+验收标准）或完整章节，保证送入 LLM 的语义完整性。
- 检索时小块命中 → 回溯取大块（+ 同 parent 的关联表格）进入生成上下文。
- 标题层级路径作为 chunk 前缀（"产品X > 订单模块 > 退款规则 > 3.2 超时处理"），显著提升上下文定位与引用可读性。

### 4.4 元数据登记（LLM 辅助 + 人工确认）

上传文档解析后，LLM 自动抽取元数据草案（product_line/module/requirement_id/version/effective_date/owner 建议），**人工在运营面板确认后才能进入"active"状态**——这是"答新不答旧"与权限过滤可靠性的根基。批量历史文档迁移时可按产品线分批确认，避免一次性人工峰值。

### 4.5 增量更新与版本管理

- 单文档更新 = 新版本解析 → 新 chunk 入库 → 旧 chunk 标记 superseded（不物理删除，保留溯源与回滚）→ 增量索引，**勿整库重建**。
- 与需求管理工具（JIRA/禅道）做定时同步：需求状态变更（如"已废弃"）自动回流 KO.status。
- 过期内容检测：effective_date 超期且 owner 未续期的条目自动降级 degrading，问答时降权并提示"该知识可能过期，建议与 owner 确认"。

## 五、检索与问答能力设计

### 5.1 查询分诊路由（Agentic RAG 分级，共识 C5）

```
用户提问 / Agent 检索请求
        │
        ▼
┌─ 分诊器（轻量分类器/规则）────────────────────────┐
│                                                   │
│ ① 事实型（"XX字段的最大长度限制是多少？"）          │
│    → 快速管线：混合检索→重排→引用组装→回答          │
│      （1-2 秒，低成本，覆盖 ~70-80% 流量）          │
│                                                   │
│ ② 关系型/多跳型（"A功能依赖哪些模块？B和C冲突吗？"）│
│    → Agentic 管线：查询分解→多轮检索→证据聚合      │
│      （8-15 秒，成本约 4 倍，调研报告 C5 数据）     │
│                                                   │
│ ③ 全局型（"本产品线退款体系的完整逻辑是什么？"）    │
│    → 阶段二：GraphRAG 社区摘要 / 层次摘要          │
└───────────────────────────────────────────────────┘
```

- 务实原则（调研报告 D6 判读 + 工程铁律）：**先让纯 RAG 跑通再加 Agent 外壳**；仅将模糊/多步问题路由进 Agentic 管线，不是所有查询都进循环。
- A1 生成检索场景多为结构化过滤+语义检索组合，默认走快速管线，API 形态返回 top-k 结构化 KO。

### 5.2 混合检索与重排（共识 C1）

> 本节描述 RAG 管线内部；生成检索（A1/A2）在此之上还有一层"Wiki 优先、RAG 兜底"的分层策略（详见 11.5-5），问答管线同样对 confirmed 知识页加权。

- **BM25**：需求编号、接口名、字段名、专名、条款号的精确匹配（向量检索对这类 token 天然弱）——零售案例：加 BM25+标签过滤后 top-5 命中率 38%→82%。
- **向量检索**：语义泛化（"优惠券核销" ≈ "券码验证销账"）。
- **RRF 融合** → **元数据过滤**（产品线/状态/密级在检索层执行）→ **Qwen3-Reranker 重排**（MTEB-R 4B 69.76 全面超 bge-reranker-v2-m3 的 57.03，2026 新默认）。
- 嵌入模型：Qwen3-Embedding（0.6B 起步，中文场景看 C-MTEB 检索单项）；选型方法论"**榜单圈定候选 + 自测 Hit@3 定生死**"——用本公司 50 份真实需求文档建小评测集实测后再定。

### 5.3 引用溯源（共识 C3，硬指标）

- 每个答案必须携带引用：文档名 + 版本 + 章节定位/页码 + 原文可点击回看（chunk_locator）。
- 引用正确率纳入评测集回归：抽取答案中每条引用，人工/LLM 裁判验证引用是否支撑对应论断。

### 5.4 拒答与兜底

- 检索置信度低于阈值 → 明确拒答 + 推荐相关文档链接 + 转人工入口（避免"检索空隙幻觉"这一通用失败模式）。
- 新旧版本冲突时主动披露："该逻辑在 v2.3 已变更，以下是现行版本（生效 2026-08-01），历史版本可点击查看"。

### 5.5 对需求生成 Agent 的暴露方式（SC-A 集成）

- **MCP server** 是首选形态（共识 C9）：提供 `search_requirements(product, module, intent, top_k)`、`get_requirement_lineage(requirement_id)`、`get_business_rule(rule_id)` 等工具。
- 兼容 REST API 供非 MCP 的存量系统集成。
- 注意 MCP 上下文税：工具 schema 常驻上下文（5 server 约 3000 token），工具数量克制、schema 精简，按需加载。

## 六、知识维护与运营体系

> 调研报告核心判断："上线后 90 天是分水岭——评测集回归、反馈回流、增量更新三件事决定它是产品还是一次性 demo。"

### 6.1 知识库可视化运营面板功能清单（H1/H2 场景，宿主：桌面端需求 Agent 内嵌，见 3.1.1）

| 模块 | 功能 |
|---|---|
| 知识浏览 | Wiki 知识页（术语/规则/演进）浏览与搜索；需求文档库导航 |
| 文档上传 | 拖拽上传 pdf/doc/docx/图片；批量导入；解析进度与失败重试；解析预览（分块结果可视） |
| 知识条目管理 | 查看/编辑 normalized 条目；标记状态（active/deprecated/draft）；合并重复条目 |
| Wiki 知识页 | AI 起草知识页（术语/规则/演进）审阅确认；confirmed 页面版本管理；来源追溯（compiled_from） |
| 元数据治理 | 元数据确认工作流（LLM 草案→人工确认）；批量修改；按产品线视图 |
| 演进链管理 | 关联新旧版本；查看需求演进时间线 |
| 权限管理 | 部门/产品线/密级三维权限；RBAC |
| 质量看板 | 问答命中率、引用率、拒答率、过期知识占比、反馈趋势（Langfuse 数据源） |
| 反馈处理 | "点不对"回流队列：错误答案→定位坏 chunk→修复（重解析/改元数据/补文档） |

### 6.2 角色与运营节奏

| 角色 | 职责 | 投入参考 |
|---|---|---|
| 知识 Owner（每产品线 1 名） | 本线知识的确权、过期复审、元数据终审 | 每周 0.5-1 人日 |
| 知识运营（平台侧 1-2 人） | 反馈处理、评测集维护、增量同步管道、月度质量报告 | 持续 |
| 全体需求工程师 | 上传、反馈、纠错 | 日常动作，无专门投入 |

运营节奏基准（调研报告案例）：某制造企业首期 1200 份文档约 3 周人工整理，上线后**每月固定 2 人日**更新增量——按公司文档规模折算预算。

### 6.3 反馈回流闭环

```
用户"点不对"反馈 → 归因分析（检索错？生成错？数据错？）
  ├─ 检索错（chunk 未命中）→ RAGChecker 定位 → 调分块/元数据/同义词
  ├─ 生成错（检索对了答错）→ 调提示词/换模型 → 评测集回归
  └─ 数据错（文档本身过期/矛盾）→ 推送知识 Owner 更新 → 演进链标记
所有修复 → 沉淀进评测集（防回归）
```

### 6.4 与研发工具链的集成

- 需求管理工具（JIRA/禅道）：需求状态同步、requirement_id 关联。
- 文档协作平台（飞书/Confluence/语雀）：调研报告产品生态证据（WeKnora 等支持直连）——阶段二做连接器，首期以导出上传为主。
- CI/CD：评测集回归接入发布流水线，答对率回落即阻断发布。

## 七、技术选型建议

### 7.1 建设模式选择（先决决策）

| 模式 | 说明 | 适合 |
|---|---|---|
| **A. 平台自建**（推荐首期评估） | 基于 Dify/FastGPT/RAGFlow/WeKnora 等开源平台私有化部署，二次开发运营面板与集成 | 快速见效（周级）、团队工程资源有限 |

## 八、实施路线图

### 阶段 0：筹备（第 1-2 周）

- 知识源盘点（4.1 表）：确定首期 P0 文档清单（建议 50-300 份核心需求文档起步——"50 份核心文档结构化解析比换强模型收益更大"）。

### 阶段 1：MVP（第 3-8 周）——单个产品线闭环

- 数据：P0 文档清洗解析入库（含元数据人工确认流程）。
- 能力：H1 上传入库 + C1/D1/D2/G1 问答（桌面 Agent，快速管线，混合检索+重排+引用）+ 运营面板基础版（上传/条目/元数据确认/反馈按钮）。

### 阶段 2：增强（第 9-16 周）——全场景接入

### 阶段 3：深化（第 17-26 周）——按数据决策增强项

- **GraphRAG 评估**（ADR-5 触发条件）：统计关系型/多跳问题占比与失败率，超阈值（建议：多跳问题占 >15% 且快速管线答对率 <60%）则启动——实施节奏参考调研报告：图谱构建 5-10 周（50 万文档级可缩短）→ 混合路由 → A/B。
- **Wiki 知识页规模化编译**：高频命中需求域由 AI 起草知识页（术语/规则/需求/FAQ 页），知识 Owner 确认后生效并在生成检索分层中优先；目标术语覆盖核心业务域 80% 高频概念，A1 流量 Wiki 命中占比达 40%+。
- 原型图/接口文档多模态入库（评估 ColPali 路线与存储成本）。
- 文档平台连接器（飞书/Confluence 直连同步）。
- 交付标志：月度质量报告机制固化，运营节奏（每月 2 人日增量更新）稳定运行；Wiki 知识页开始反哺检索质量（同域问题答对率可见提升）。

## 九、评测体系与验收标准

### 9.1 评测集建设

- 规模：起步 50-100 条 → 成熟期 200-500 条（共识 C4 口径）。
- 构成三类：
  - **高频事实型**（60%）："XX 报表的统计口径？"——考检索精度。
  - **多跳关系型**（25%）："A 功能与 B 模块的依赖约束？"——考路由与聚合。
  - **拒答/边界型**（15%）："库里没有的逻辑"——考幻觉治理（必须拒答而非编造）。
- 出题人：需求工程师 + 业务分析师（真实提问分布），运营负责入库与去重。

### 9.2 指标体系

| 层 | 指标 | 目标 | 工具 |
|---|---|---|---|
| 检索 | Hit@3 / nDCG@10 | Hit@3 ≥ 80%（A1 生成检索验收线） | RAGAS 上下文召回 / 自测脚本 |
| 生成 | faithfulness（忠实度）、答案正确率 | faithfulness ≥ 90% | RAGAS / DeepEval |
| 引用 | 引用率 / 引用正确率 | 100% / ≥ 90% | LLM 裁判 + 抽检 |
| 幻觉 | 拒答正确率（该拒的拒了） | ≥ 95% | 边界评测子集 |
| 工程 | P95 时延 / token 成本 | ≤8s（快速管线 ≤3s）| Langfuse |
| 业务 | 周活问答用户 / 需求生成引用采纳率 / 反馈解决时长 | 上线 3 个月周活 ≥ 需求团队 60% | 质量看板 |

### 9.3 回归机制

- 任何变更（分块策略/嵌入模型/提示词/平台升级）→ 评测集全量回归 → 答对率回落超 2pp 阻断发布。
- 评测数据集与坏例归档进 Langfuse，形成"坏例库"——每次修复沉淀为回归用例。

## 十一、交付方案：基于 WeKnora 快速落地 20 个场景

### 11.1 为什么是 WeKnora（对本方案的贴合度）

### 11.3 RAG 方案：知识库初始化与检索配置

**（1）知识库划分**——按"产品线 × 密级"建库（WeKnora 租户/知识空间机制），映射 KO.confidentiality：

| 知识库 | 内容 | 权限 |
|---|---|---|
| KB-需求-商城线 | 商城 PRD/SRS/规则/变更 | 商城线全员+需求团队 |
| KB-需求-支付线 | 支付线文档 | 支付线全员（保密级单列 KB-需求-支付-保密） |
| KB-术语字典 | 全公司统一术语表/数据字典 | 全员可读，Owner 维护 |
| KB-评审归档 | 评审纪要/决策记录 | 需求团队 |

**（2）入库管线**（对应第四章，WeKnora 解析服务承载前段，二开承载后段）：

```
上传(docx/pdf/扫描件) → WeKnora 解析（版面/表格/OCR）
  → 【二开】父子分块增强：child 200-400 字 / parent 800-1500 字，
     标题路径前缀（"商城>订单>退款规则>5.2"），表格整块不拆
  → 【二开】元数据登记：LLM 抽取五要素草案 → 运营面板人工确认 → active
     （requirement_id / version / effective_date / owner / 密级；
      变更记录文档额外抽取 related_kos 演进链）
  → 向量化（Qwen3-Embedding）+ BM25 建索引 → 入库
```

**（3）检索配置**（对应 5.1/5.2 节）：

- 检索策略：混合检索（向量+BM25+RRF）+ Rerank 开启；top-k：候选 20 → 重排后 5。
- 分诊路由（P1 二开，挂在问答入口与 MCP 工具层）：轻量分类器判别"事实型/多跳型"——事实型直连 WeKnora RAG；多跳型走 WeKnora ReAct Agent 模式（其"检索→工具→沙箱"循环即 Agentic 管线），省去自研编排。
- 拒答兜底：检索置信度阈值（重排分 < 阈值）→ 模板化拒答 + 相关文档推荐。
- 语义缓存：高频问题（D1/D2 类术语与编号查询）缓存命中，降时延与成本。

**（4）评测基线**（对应第九章）：初始化完成后立即用 50-100 条评测集跑 RAGAS 基线，作为后续一切调参的对照组。

### 11.5 Wiki 方案：结构、编译与治理（双范式的落地细节）

**（1）Wiki 空间结构——顶层按业务域，类型作页面属性**

结构选型对比（为什么不用"按类型分顶层"）：

| 方案 | 结构 | 问题/优势 |
|---|---|---|
| 按类型分顶层（术语区/规则区/演进区/FAQ 区） | 类型驱动 | ❌ 割裂业务域：查"退款"要跨 4 个目录；与用户"按功能域工作"的心智不符；AI 按域生成时需拼装多个目录的片段 |
| **按业务域分顶层，类型作页面属性**（采用） | 域驱动 | ✅ 与 KO.metadata.module 对齐、与需求工程师心智一致；一个域的知识（术语+规则+需求+FAQ）自然聚合；域内互链密度高；直接支撑"域上下文包"式生成检索（见下） |

采用结构：

```
Wiki 空间（每产品线一个，权限随知识库）
├── 00-总览/                     # 产品线业务地图：域清单、核心流程、干系人
├── 10-订单/                     # ── 业务域（对应 KO.module 一级）──
│   ├── _index.md               # 域首页：本域知识地图 + 核心规则/需求索引
│   ├── 术语-待履约.md           # 类型作命名前缀：术语-/规则-/需求-/FAQ-
│   ├── 术语-券码.md
│   ├── 规则-退款超时.md         # 触发条件/动作/例外/生效版本/来源KO
│   ├── 规则-取消订单.md
│   ├── 需求-REQ-2024-0871.md    # 需求条目页：背景/规则/验收标准 + 演进时间线（v1→v2→v3）
│   └── FAQ-预售退款.md
├── 20-会员/
├── 30-营销/
└── 90-全局/                     # ── 跨域知识 ──
    ├── 全局术语-客户号.md        # 公司级口径（vs 域内术语，本身就是口径治理）
    ├── 跨域流程-下单到履约.md
    └── 规范-需求文档编写规范.md
```

设计规则：

- **域即目录**：顶层业务域与 KO.metadata.module 一级对齐，KO 编译时按 module 自动归位（`规则-退款超时.md` ← KO-08712），无需人工判断归属。
- **类型即属性**：页面类型用命名前缀 + front-matter `type` 字段双重表达（检索加权用 type 字段，比解析目录路径可靠）；不再为类型单设目录。
- **每域一个 `_index.md` 域首页**：本域知识地图（术语/规则/需求清单+链接），既是人的导航入口，也是 AI 的"域上下文包"索引起点。
- **演进内嵌**：需求变更历史以时间线小节内嵌在需求页；仅变更超过 5 次的复杂需求才拆独立演进页——E1 变更追溯默认读页内时间线。
- **术语两级**：全局术语（公司级口径，如"客户号"）归 90-全局；域内术语（如订单状态"待履约"）归域内——归属判定本身就是口径治理动作。
- **命名规范**：`{类型前缀}-{名称}.md`，同域页面按名称排序天然按类型分组，一眼看全本域知识。

**页面模板**（以业务规则页为例，Markdown 固定 front-matter 保证可检索可治理）：

```markdown
---
type: rule            # rule / term / evolution / faq
product_line: 商城
module: 订单-退款
requirement_id: REQ-2024-0871
effective_version: v2.3
effective_date: 2026-08-01
owner: 李四
review_status: confirmed
compiled_from: [KO-08712, KO-08715]
---
# 退款超时规则
## 规则（normalized 条目）
触发条件：… 动作：… 例外：…
## 适用范围与例外
## 生效与演进（页内时间线：v1→v2→v3；变更超 5 次拆独立演进页）
## 来源（compiled_from 原文引用，可点击回跳）
```

**（2）编译管线**——"RAG 用出来 → AI 起草 → Owner 确认"（ADR-2 的人在回路）：

```
触发：某需求域检索命中频次进入 Top 20%（Langfuse 看板识别）
  → AI 起草：WeKnora Wiki 模式对选定文档集自动生成互链页面（初稿）
  → 结构规整：【二开】按页面模板重排（front-matter 元数据 + compiled_from 回填）
  → Owner 审阅：运营面板确认工作流——可改可驳回；确认后 review_status=confirmed
  → 生效：confirmed 页面进入检索加权（同域查询优先返回知识页而非原文），
     并出现在 Wiki 空间供人浏览；WeKnora Wiki 自带版本回滚
```

**（3）编译节奏与量化目标**：

| 阶段 | 动作 | 量化目标 |
|---|---|---|
| P1 末 | 首批编译：试点产品线 Top 高频域 | 术语表 50 词条 + 核心规则页 30 页 |
| P2 | 规模化：全产品线推进 | 术语覆盖核心业务域 80% 高频概念；规则页覆盖 P0 文档域 60% |
| 持续 | 月度增补：新升高频域 + 过期页复审 | 每月新增 ≤20 页（控制 Owner 审阅负担）；过期页自动降级提醒 |

**（4）反哺验证**：同域评测问题在"仅原文 RAG"与"知识页加权"两种配置下对比答对率——Wiki 的价值必须被评测证明（工程原则 5），预期术语/规则类问题提升显著，若不达标回查编译质量。

**（5）Wiki 用于需求生成：与 MCP+RAG 的对比与融合**

Wiki 能否服务 A1 历史参考检索？能，且在高质量域上**优于**纯 MCP+RAG，但两者不是二选一：

| 维度 | MCP+RAG（检索原文 chunk） | Wiki 知识页（确认过的结构化知识） |
|---|---|---|
| 内容质量 | 原文片段，质量随文档参差 | Owner 确认过的知识，噪声低、口径统一 |
| 完整性 | chunk 碎片，需拼装 | 一个域/一条规则的完整知识单元 |
| token 效率 | 需多 chunk 组上下文，冗余高 | 域首页+规则页即"域上下文包"，密度高 |
| 时效性 | 文档入库即可检索，**零冷启动** | 需编译+确认，滞后 1-4 周 |
| 覆盖面 | 全量文档域 | 仅 Top 高频域（编译覆盖率有限） |
| 演进与一致性 | 新旧版本靠元数据过滤，仍有混入风险 | 页面即现行版（编译时已消解版本） |

结论（写入 A1 的检索策略）：**分层检索——Wiki 优先、RAG 兜底**：

```
A1 生成检索请求 search_requirements(product, module, intent)
  ① 命中 confirmed 知识页？→ 返回域上下文包（_index + 相关规则/需求页）
     ——质量高、完整、token 省；随编译覆盖率扩大份额
  ② 未命中（长尾域/新需求域）→ 回落 RAG 管线（混合检索+重排）
     ——覆盖全量，零冷启动
  ③ 命中统计回流 Langfuse → 未命中频次高的域进入编译候选队列
     ——RAG 的使用驱动 Wiki 的生长（与编译触发条件闭环）
```

对生成质量的影响路径：写"预售退款"需求时，若退款域已有 confirmed 知识页，AI 拿到的是"术语定义+现行规则+例外清单+演进脉络"的完整域包，而非十几段原文碎片——生成需求与现行逻辑的一致性、术语准确度、验收标准完整度都更高。**Wiki 份额随阶段递增的量化表达**：P1 末 Wiki 命中占 A1 流量约 20%（首批编译域），P2 目标 40%+（覆盖 80% 高频域后）——作为检索质量的持续改进指标纳入月度报告。
