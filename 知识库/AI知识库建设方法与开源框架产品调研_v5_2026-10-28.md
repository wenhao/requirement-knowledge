## 核心结论（SCQA 金字塔塔尖）

**S 情境**：企业普遍要用 LLM + 私有知识构建 AI 知识库。2023-2024 年 RAG 是唯一答案，2025 年生成式 LLM Wiki 路线兴起，2026 年 Agent 记忆与上下文工程成为第三股力量。

**C 冲突**：①单一向量检索在多跳推理、全局理解上结构性失灵；②"长上下文杀死 RAG"论战虽已收敛（混合架构成为默认），但"上下文 rot"（输入越长性能越差）刚被系统证实；③产品从四层数十个膨胀为八层 150+ 个，且 2025-2026 出现"归档潮"（h2oGPT、Verba、Reor、Vanna 等一代明星项目停更），Star 数与可用性已经脱钩；④80% 企业 AI 项目失败率（RAND）与 95% 试点无财务影响（MIT NANDA）提示工程方法比工具选型更致命。

**Q 问题**：AI 知识库到底该怎么建、怎么选、怎么活过 90 天？

**A 答案（核心判断）**：
- **[外] 三线叙事并存且加速融合**：检索式（从海量原文找答案）、生成式（把资料沉淀为结构化知识）、上下文工程/Agent 记忆（把知识当一等资源做存取调度）——WeKnora 三模式一体、OpenViking 上下文数据库、MemOS 记忆操作系统分别代表三线的产品化形态（https://weknora.weixin.qq.com/ 、https://github.com/volcengine/OpenViking 、https://memos.openmem.net/）
- **[外] 检索式按"混合架构 + 查询分诊路由"演进，长上下文不替代而收编**：<200K token 全塞、200K-2M 看并发成本、>2M 必须 RAG；Chroma Context Rot 报告测 18 个前沿模型输入越长性能越差，"全量塞上下文"已被证伪（https://codefarm.in/blog/gen-ai/long-context-vs-rag-2026 、https://aiwiki.ai/wiki/chroma）
- **[外] 2026 组件层发生代际更替**：嵌入/重排进入 Qwen3 时代（8B 曾列 MTEB 多语言榜 #1，Reranker 全面超越 bge-reranker-v2-m3）；视觉文档检索 ColPali 路线免 OCR 工业落地；图谱+向量融合数据库（HelixDB/Kuzu/CozoDB）冲击双组件架构；pgvector 生态固化（pgvecto.rs 已停维护）（https://qwenlm.github.io/blog/qwen3-embedding/ 、https://github.com/illuin-tech/colpali）
- **[外] 成败在数据治理与运营，不在模型**：清洗约占 40% 工作量；引用溯源硬指标；50-500 条评测集；上线后 90 天是分水岭——失败复盘（法律科技公司 18 万份合同 RAG 覆盖率从 100% 主动降到 87% 换正确性）反复验证（https://simorconsulting.com/blog/when-rag-failed-a-knowledge-retrieval-project-post-mortem）
- **[外] 选型必须带生命周期意识**：八层格局中没有全维度最优产品；Microsoft GraphRAG、STORM 维护放缓，h2oGPT/Verba/Reor/Vanna 已归档——选型前先查仓库最近提交（https://www.thirdbrain.tech/KB-AI/ai-memory/graphrag）

## 关键要点（Key Takeaways）
- 三条建设路线按知识形态分工：原文问答走检索式、知识沉淀走生成式 Wiki、Agent 长期个性化走记忆系统；头部产品正把三者装进同一个壳
- 个人/小团队（<40 万词）先试 LLM Wiki：一目录 Markdown + 大上下文 LLM，基建近零；"向量检索是大锤，结构化 Markdown 是手术刀"
- Agent 记忆赛道 2026 年爆发：Mem0（68k★）、Hindsight（54.5k★）、OpenViking（41k★）、TencentDB Agent Memory（30k★）——记忆系统与知识库的边界正在消失
- 建知识库先治数据再调模型：50 份核心文档结构化解析与元数据登记，比换更强模型收益更大；嵌入不含结构元数据是法律 RAG 失败案例的根因
- 检索质量三板斧（混合检索+重排+父子分块）之上，2026 年新增第四斧：**推理模型中途触发检索**（Search-o1 类，多跳任务 +30%）
- 引用溯源做成硬指标 + 评测集回归（RAGAS/DeepEval/promptfoo 已可进 CI/CD），幻觉治理第一道闸
- 选型速记：中文快速起步 MaxKB/FastGPT；复杂文档 RAGFlow；多应用编排 Dify；双范式一体 WeKnora；企业统一搜索 onyx/Coco AI；数据问答 Wren AI；代码团队 LlamaIndex+LangGraph；生产可审计 Haystack；全局理解 Microsoft GraphRAG（维护模式）；增量省钱 LightRAG 或 RAG-Anything；自动维基 STORM（维护放缓）；Agent 记忆 Mem0/Letta/OpenViking
- RAG 项目分水岭在上线后第 90 天：评测集回归、反馈回流、增量更新三件事决定它是产品还是一次性 demo
- 向量库已商品化：纯向量库窗口关闭，价值上移到知识层/上下文层——已有 PG/ES 基建的团队优先 pgvector/ParadeDB/Infinity，不要为"向量"引入新组件

# 第二部分：技术全景——三线叙事（论据支柱一：是什么）

## 2.1 总纲：从双范式到三线叙事

| 维度 | 检索式（RAG 系） | 生成式（LLM Wiki / 知识策展系） | 上下文工程 / Agent 记忆系（2025-2026 新增） |
|---|---|---|---|
| 核心动作 | 查询时**检索**原始文档片段，交给 LLM 组织答案 | 入库时 LLM 主动**编译**原始资料为结构化互链 Wiki | 把知识/记忆当一等资源做**存取调度**：压缩、笔记、子代理、按需加载 |
| 知识形态 | 向量索引+分块原文（原文不动） | 主题文章+反链+索引（知识被重写、浓缩、互链） | 记忆立方（明文/KV-cache/参数三态）、分层记忆管线、上下文窗口管理 |
| 基础设施 | 向量库+embedding+检索管线 | 一目录 Markdown+大上下文 LLM | 记忆引擎（Mem0/MemOS）+ 上下文数据库（OpenViking）+ MCP |
| 规模边界 | 大规模企业数据集 | 个人到部门级（约 10 万-100 万词） | 会话级到组织级（跨会话、跨 Agent、跨应用共享） |
| LLM 角色 | 被动检索工具 | 主动知识编辑/策展人 | 上下文的消费者与管理者（compaction/记忆写入） |
| 代表 | Dify/RAGFlow/FastGPT 等 RAG 平台 | Karpathy LLM Wiki、STORM/Co-STORM、WeKnora Wiki 模式 | Anthropic 上下文工程方法论、Mem0、Letta、MemOS、OpenViking、TencentDB Agent Memory |
| 适用 | 知识量大、更新频繁、多用户权限隔离 | 研究者/小团队沉淀领域知识 | Agent 长期运行、个性化、跨会话知识积累 |

三线不互斥且加速融合：WeKnora 把 RAG+Agent+Wiki 装进同一产品；OpenViking 用 viking:// 虚拟文件系统统一记忆/RAG/技能；TencentDB Agent Memory 把会话/文档/代码治理为四类记忆资产（Chat Memory、Skill、LLM-Wiki、Code-Graph）——**"检索找答案、编译沉淀知识、调度管上下文"正在成为企业知识中枢的三件套**（来源：[kalinga.ai](https://kalinga.ai?p=1773/)、[Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents/)、[GitHub/volcengine](https://github.com/volcengine/OpenViking)）。

## 2.2 检索式谱系：五代 RAG 与推理增强新变量

| 范式 | 核心机制 | 主要提升 | 成熟度/时点 |
|---|---|---|---|
| Naive RAG | 索引→检索→生成单次流水线 | 基线接地（grounding） | 2023 年标准，2025 年起被认为不适合生产 [外](https://aiwiki.ai/wiki/retrieval_augmented_generation/revisions/1) |
| Advanced RAG | 检索前优化（查询改写/分解/HyDE）+ 检索后处理（重排/压缩/过滤） | 精度提升、噪声降低 | 2024 年起成为生产主流 [外](https://www.manning.com/preview/a-simple-guide-to-retrieval-augmented-generation/chapter-6) |
| Modular RAG | 可插拔模块：路由/记忆/融合/搜索/任务适配 | 灵活性、按需编排 | 企业差异化场景 [外](https://www.aiknots.com/2026/03/a-deep-dive-into-three-pillars-of-rag.html) |
| GraphRAG | 知识图谱 + 向量双检索 | 多跳推理、全局主题理解 | 微软 2024 提出，2026 进入生产可选 [外](https://www.zata.cc/p/graph-rag-%E5%BC%80%E6%BA%90%E9%A1%B9%E7%9B%AE%E5%85%A8%E6%99%AF%E4%BB%8E%E5%BE%AE%E8%BD%AF-graphrag-%E5%88%B0-lightrag/) |
| Agentic RAG | Agent 自主规划检索：迭代/反思/纠错/多智能体 | 复杂任务处理 | 2026 年企业主流形态 [外](https://callsphere.tech/blog/agentic-rag-new-architecture-powering-enterprise-knowledge-agents) |
| **推理增强检索（新）** | 推理链**中途**检测知识缺口动态触发检索（Search-o1/Search-R1/ReaLM-Retrieve） | 多跳任务较传统 RAG +30%；ReaLM-Retrieve 平均 +10.1% F1 且检索调用 -47% | 2025-2026 最热论文方向；工业落地以 prompt 级 agentic 检索为主 [外](https://search-o1.github.io/) |

旁支变体：**Self-RAG**（生成中自我评估是否需要检索、答案是否接地，官方库 2.4k★）、**CRAG**（检索评估器发现弱证据时触发纠错）、**记忆增强 RAG**（HGMem、MiA-RAG 持久化认知结构）、**MemoRAG**（BAAI，轻量 LLM 先生成全局记忆线索再引导精确检索，2.3k★，超长文档全局理解）、**LongRAG**（检索"长单元"+长上下文打包，弱化分块）、**RAPTOR**（斯坦福，层次聚类+递归摘要建树，1.8k★，跨粒度检索）、**StructRAG**（中科院，推理时把信息重构为图/表/树混合结构）。

**性能量级参考**：Agentic RAG 对比单轮 RAG，复杂查询答案准确率 +47%、多部分问题完整度 +63%（LlamaIndex 2026-02 基准，5000 条企业复杂查询）；代价是每查询 3-7 次 LLM 调用、响应 8-15 秒、单查询成本约 4 倍 [外](https://callsphere.tech/blog/agentic-rag-new-architecture-powering-enterprise-knowledge-agents)。Uber 内部高级 Agentic RAG 可接受答案占比相对 +27%、错误建议 -60% [外](https://www.lumevalley.com/article-6465.html)。Anthropic 多子代理研究系统自评比单代理 +90% 效果但约 15 倍 token [外](https://www.anthropic.com/engineering/built-multi-agent-research-system)。

**Long-Context 之争的判决**：Gemini 2M/GPT-4.1 1M/Claude 1M 使"全量塞"成为可能，但 ①成本按 token 计费，万级日查询下 10-20 倍于 RAG；②Chroma Context Rot 报告测 18 个前沿模型（GPT-4.1/Claude 4/Gemini 2.5/Qwen3）输入越长性能越差，LongMemEval 上 300 token 焦点提示远胜 113K 全历史；③权限过滤、新鲜度更新天然属于检索层。共识决策树：<200K 全塞、200K-2M 看并发、>2M 必须 RAG——**"RAG 定位 5000 相关 token，长上下文负责在其上推理"**（来源：[xqa.io](https://xqa.io/blog/stopped-using-rag-context-window-killed-it)、[codefarm](https://codefarm.in/blog/gen-ai/long-context-vs-rag-2026)、[lobehub](https://lobehub.com/skills/claude-dev-suite-claude-dev-suite-long-context-vs-rag)）。

## 2.3 生成式谱系：LLM Wiki 与知识策展

**Karpathy 的 LLM Wiki 工作流**（2026 年公开，via GitHub Gist 广泛传播）：
- 核心理念："你几乎从不手工编写或编辑 wiki——这是 LLM 的领地"。LLM 扮演 research librarian（研究馆员），不是搜索引擎
- **四阶段循环流水线**（来源：[DAIR.AI Academy](https://academy.dair.ai/blog/llm-knowledge-bases-karpathy)）：
  1. **摄取 Ingest**：Obsidian Web Clipper 把网页转 Markdown 落入 raw/ 目录；arXiv 论文、GitHub 仓库、数据集同样入 raw/——人类唯一大量介入的环节
  2. **编译 Compile**：LLM 增量读取 raw/，编译为结构化互链 Wiki——按主题组织的概念文章（约 100 篇/40 万字）、总索引、反链与交叉引用；派生产物含 Marp 幻灯片、matplotlib 图表
  3. **查询与增强 Query & Enhance**：问答 Agent 跨文章回答复杂研究问题，答案回写进 wiki——"每次探索都累积"
  4. **体检 Lint**：LLM 扫描不一致信息、经 web 搜索补缺失、发现新概念关联——知识库自愈
- **关键实测结论**：约 100 篇/40 万字规模下复杂问答几乎不需要 RAG；"向量检索是大锤，结构化 Markdown 是手术刀"（来源：[kalinga.ai](https://kalinga.ai?p=1773/)）
- 社区开源实现：obsidian-llm-wiki（摄取 3B-8B/编译 7B-14B/默认 Ollama 全离线）、llmwiki（MCP 接 Claude）、Nashsu/llm_wiki 桌面版；**Obsidian 官方 obsidian-skills**（约 50.2k★）教 Claude Code/Codex 等 Agent 操作 Obsidian 库，标志着笔记工具正式接入 Agent 生态（来源：[inside.com.tw](https://www.inside.com.tw/article/41745-obsidian-vault-pipelin)、[github.locker note-taking 榜](https://github.locker/topics/note-taking)）

**斯坦福 STORM / Co-STORM：自动维基写作的学术标杆**：
- STORM（NAACL 2024，斯坦福 OVAL）：给定主题自动完成"研究→大纲→带引用类维基长文"全流程；预写作阶段多视角挖掘+模拟作者向专家提问；维基编辑者评估组织性 +25pp、覆盖广度 +10pp；超 7 万人试用（来源：[项目页](https://storm-project.stanford.edu/research/storm/)）
- Co-STORM（EMNLP 2024）：人机协作知识策展，多视角 AI agent 讨论+人类随时插问，探索"未知的未知"
- 工程形态：MIT 开源（stanford-oval/storm，约 31.5k★），`knowledge-storm` Python 包；**注意维护状态**：最后 merge 2025-09、最后发版 2025-01，学术原型而非持续维护产品

**生成式的 2026 年产品化扩展**：
- WeKnora Wiki 模式（自动互链 Wiki+可视化知识图谱+版本回滚）——国内落地样本
- Open Notebook（约 40k★，MIT）：自托管 NotebookLM 平替，1-4 人播客生成+20+ 模型商（来源：[enlisted.directory](https://enlisted.directory/tools/open-notebook)）
- TencentDB Agent Memory 把 LLM-Wiki 作为四类记忆资产之一——生成式范式被记忆系统收编为"知识资产"（来源：[GitHub/TencentCloud](https://github.com/TencentCloud/TencentDB-Agent-Memory)）

## 2.4 上下文工程与 Agent 记忆（第三线，2025-2026 兴起）

**Anthropic《Effective context engineering for AI agents》（2025-09-29）** 正式定义上下文工程为独立学科："上下文是有限资源，边际收益递减"（context rot）。四大技术：
1. **Compaction 压缩**：上下文编辑自动清除过期工具调用
2. **结构化笔记 / agentic memory**：NOTES.md 模式，重要信息写入持久文件
3. **子代理架构**：主代理规划、子代理用干净上下文深挖后仅回传 1-2K token 摘要
4. **Just-in-time 上下文加载**：按需取用而非全量预载
产品化证据：Claude 平台 context editing + memory tool，内部评测 agentic search +39%，100 轮搜索任务 token 消耗 -84%（来源：[Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents/)、[Anthropic News](https://www.anthropic.com/news/context-management)）。

**记忆操作系统的技术形态（以 MemOS 为代表）**：统一明文记忆/激活记忆（KV-cache）/参数记忆（LoRA）三态于 MemCube 容器，带生命周期（生成→激活→合并→归档→冻结）、MemScheduler 调度、溯源审计（来源：[MemOS 文档](https://memos-docs.openmem.net/cn/open_source/home/memos_intro/)）。竞品生态：Mem0（抽取-更新-冲突消解分层管线，图记忆可选，68k★）、Zep/Graphiti（双时态知识图谱，时序事实失效）、Letta（原 MemGPT，OS 式分页记忆+sleep-time compute）、A-MEM（NeurIPS'25，Zettelkasten 式记忆自组织）。

**与知识库的关系判读**：记忆系统解决"Agent 用出来的知识"（会话、偏好、技能），知识库解决"组织既有的知识"（文档、制度、 wiki）——2026 年两者在产品层合流（TencentDB Agent Memory、OpenViking、WeKnora Agent 模式）。企业视角的正确姿势：**文档知识走 RAG 管线治理，行为知识走记忆管线沉淀，两者通过 MCP 互访**。

## 2.5 融合终态：企业级"知识中枢"参考架构

自托管企业知识大脑的组件清单（来源：[app-lab.ai](https://app-lab.ai/blog/ai-agent-company-knowledge)，v5 扩充）：知识摄取（爬 SharePoint/Confluence/Jira/ServiceNow/wiki）→ 文档解析（MinerU/Docling/PaddleOCR/TextIn）→ 向量库（pgvector/ParadeDB 或专用向量库）+ 知识图谱（Neo4j/FalkorDB，可选）→ GraphRAG 管线（按需）→ 记忆层（Mem0/Letta，Agent 场景）→ MCP server（向 agent 暴露 search_wiki/query_knowledge_graph 等工具）→ RBAC 部门级隔离 → 审计日志 → 持续爬取 → 过期内容检测 → 评测与可观测（RAGAS+Langfuse/Phoenix）→ 自托管部署。

MCP（"AI 的 USB-C"）与知识图谱的结合被视为企业 GraphRAG 真正可落地的技术交汇点（来源：[gtc.noqta.tn](https://gtc.noqta.tn/en/blog/graphrag-knowledge-graphs-enterprise-ai-2026)）。知名知识库类 MCP server：官方 mcp-server-memory（>2k★）、Mem0 MCP（graph+vector）、ApeRAG（>500★，GraphRAG+向量+全文三路混合）、Neo4j MCP、Qdrant MCP（来源：[awesomeclaude.ai](https://awesomeclaude.ai/how-to/give-claude-memory)）。已知税负：每个 server 工具 schema 常驻上下文，5 个 server 约 3000 token，需动态加载缓解。

# 第三部分：建设方法（论据支柱二：怎么建）

## 3.1 检索式：五步建设法

综合企业实战资料（joto.ai、ii-vv.com、tokenstar.ai、bitechnology.com）：

**第一步：收集与数据治理（决定成败的隐形环节）**
- 盘点知识源：制度、手册、FAQ、工单、产品资料、图片、表格，标注版本与责任人
- 清洗：去水印页眉、合并重复版本、扫描件 OCR 后人工校对——约占项目工作量 40%
- 权限矩阵：每份文档标密级与部门归属，权限过滤在检索层执行而非应用层（欧盟 AI Act 合规基线）
- 高频陷阱：新旧版本混存导致"答旧不答新"——某银行员工问答引用 2019 利率规则，根因是 PDF 与向量库同步延迟（来源：[CSDN 失败复盘](https://blog.csdn.net/yiyiyi0322/article/details/165334921)）

**第二步：解析与切分**
- 深度文档理解：合同条款、表格、扫描件需版面级解析（RAGFlow DeepDoc、MinerU、Docling、PaddleOCR/PP-StructureV3、Unstructured、TextIn），300 页 PDF 不切分直接入库命中率极差
- 切分策略：语义段落切块（300-500 字）保留标题层级，表格整块不拆；进阶父子分块——小块定位、大块保语义完整
- 反面案例：某金融客户 512 token 定长切片把"不保本"风险警示拦腰截断（来源：[zvenue](http://www.zvenue.cn/info/enterprise-rag-failure-modes.html)）
- 元数据是法律 RAG 失败案例的根因：18 万份合同语义相似但法律上不适用（错合同类型/司法辖区/被修订版本）——嵌入不含结构元数据、评测集由工程师而非律师构造；重建为元数据过滤+结构化检索后覆盖率从 100% 主动降到 87% 换正确性（来源：[simorconsulting 复盘](https://simorconsulting.com/blog/when-rag-failed-a-knowledge-retrieval-project-post-mortem)）

**第三步：索引与检索策略**
- 混合检索标配：BM25+向量并行、RRF 融合；专名/编码/条款号靠关键词，语义泛化靠向量
- 重排：cross-encoder 对 top-20 联合打分；2026 年新默认 Qwen3-Reranker（MTEB-R 4B 69.76 全面超 bge-reranker-v2-m3 的 57.03），中文榜单看 C-MTEB 检索单项
- 嵌入选型方法论："榜单圈定候选+自测 Hit@3 定生死"——通用基准分数不保证自有文档表现（来源：[Qwen 官方](https://qwenlm.github.io/blog/qwen3-embedding/)、[中文 Embedding 选型指南](http://mp.weixin.qq.com/s?__biz=Mzg3Njk4MjkyNg==&mid=2247483713&idx=1&sn=7682c15b023438204b9593ae6befdeee)）
- 歧义修复案例：某零售 top-5 命中率仅 38%（"Apple"歧义），加 BM25+标签过滤后升至 82%（来源：[zvenue](http://www.zvenue.cn/info/enterprise-rag-failure-modes.html)）

**第四步：评测与校验**
- 评测集：50-100 条真实业务问题起步，成熟期 200-500 条；含高频/拒答/边界三集
- 评测框架：RAGAS（faithfulness/上下文召回等）+ DeepEval（PyTest 式 14+ 指标进 CI/CD）+ promptfoo（声明式 YAML 断言）；诊断"检索错还是生成错"用 RAGChecker（chunk 级引用、检索与生成解耦指标）
- 每次改版先跑评测集回归，答对率回落即回滚；引用硬指标：每个答案必须带出处

**第五步：业务接入与运营治理（分水岭在上线后第 90 天）**
- 接入真实入口（网页、企微、客服台），保留转人工兜底
- 反馈闭环："点不对"回流为标注数据；增量更新管道（版本管理+增量索引，勿整库重建）
- 监控口径：时延、命中率、引用率、token 成本、人工介入率——Langfuse/Phoenix/Opik 三选一做 trace
- 运营节奏参考：某制造企业首期 1200 份文档约 3 周人工整理，上线后每月固定 2 人日更新增量 [外](https://www.ii-vv.com/146)
- 警惕"上线即衰败"：某金融服务团队向量库 3 个月未重索引、引用过期利率，上线 6 周支持升级率 +34%；RAG 相关故障占生产 AI 问题 1/3-1/2（来源：[channel.tel](https://www.channel.tel/blog/knowledge-base-bottleneck-why-rag-alone-isnt-enough-production-agents)）

## 3.2 GraphRAG 决策：何时上图谱

**四阶段 GraphRAG 工程流水线**（来源：[mukebb.blog.csdn.net](https://mukebb.blog.csdn.net/article/details/166679509)）：
1. 实体关系抽取：LLM 输出三元组，去重与冲突消解（同名不同实体、同义不同名合并）是难点
2. 图谱构建存储：入图数据库（Neo4j/Neptune/ArangoDB/NebulaGraph/TuGraph），大规模库用 Leiden 社区检测划分语义社区
3. 查询路由（关键设计）：事实型问题走向量检索，关系型/全局型问题触发图检索
4. 上下文组装：图检索结果（实体、关系路径、社区摘要）与原文片段一起进提示词，区分"结构化事实"与"原文片段"并标注引用

**成本与选型判断**（来源：[delos.so](https://delos.so/blog/graphrag-vs-vector-search-enterprise-knowledge-retrieval)）：
- GraphRAG 索引成本比向量贵 10-50 倍；文档日更频繁、缺 ML 基建、预算受限 → 向量 RAG 更实际
- 适用：多跳推理、关系准确性合规攸关（监管/法律/金融）、实体消解、已有企业图谱、研发/科学检索
- 实施路线图：基线向量 RAG（1-4 周）→ 图谱构建（5-10 周，50 万文档）→ 混合路由（11-13 周，标注 500-1000 条查询训轻量分类器）→ 生产调优（14-16 周 A/B）→ 规模治理（持续）
- 常见坑：过度建图（5-10 个实体类型起步）、图遍历延迟（580ms 可飙至 2-3 秒，限跳深+缓存）、抽取质量绑定 LLM 能力、无向量回退策略

**2026 年图谱层新选项**：
- 一体化图+向量库：HelixDB（Rust，图 OLTP 原生向量+全文，6.2k★）、Kuzu（嵌入式属性图，内置向量+全文，4k★）、CozoDB（关系-图-向量三合一，4.1k★）——直接省掉"图库+向量库"双组件
- 文档→图谱自动化：Neo4j LLM Graph Builder（5.3k★，PDF/网页/YouTube→Cypher 入图）、Graphify（137k★，代码库/文档/SQL/PDF 转可查询知识图谱，本地确定性 AST 解析，无向量库）
- 多模态图谱：RAG-Anything（港大 HKUDS，24.2k★，MinerU 解析+LightRAG 图谱，全模态文档入图）

## 3.3 Agentic RAG：何时加 Agent

- 六种关键架构模式：路由 Agent、查询规划、ReAct、Self-RAG、CRAG、GraphRAG（来源：[zylos.ai](https://zylos.ai/research/2026-01-09-agentic-rag/)）
- 生产化最佳实践：语义缓存去重（Redis LangCache）、可观测性（89% 组织已建）、多模型策略（75%+）、幻觉治理优先于扩规模
- 务实用法：并非所有查询都需要 Agentic 循环；生产系统仅将模糊/多步问题路由进 Agentic 管线（来源：[superkind.ai](https://superkind.ai/ai-lexicon/agentic-rag)）
- 前沿增量（2025-2026）：推理模型×检索——Search-o1（EMNLP 2025 Oral，推理中自检不确定点动态触发检索，多跳 +30%）、Search-R1（搜索引擎当 RL 环境，端到端学"何时搜、搜什么"）、ReaLM-Retrieve（推理步级不确定性检测，+10.1% F1 且检索调用 -47%）；系统性综述分出 RAR（推理增强检索）/ReAR（检索增强推理）两方向，"过度思考 token 膨胀"是落地税（来源：[search-o1](https://search-o1.github.io/)、[综述 arXiv 2506.10408](https://ar5iv.labs.arxiv.org/html/2506.10408)）
- 架构铁律：先让纯 RAG 跑通再加 Agent 外壳；上来就多 Agent，出问题分不清是检索还是编排的锅 [外](https://aibotgo.net/blog/open-source-rag-framework-comparison-2026)

## 3.4 生成式：LLM Wiki 四阶段建设

即 2.3 节 Karpathy 流水线（摄取→编译→查询增强→lint），工程要点：
- 起步最小可行结构：本地目录 + 5 份结构良好的 Markdown（YAML frontmatter + 标题层级 + 内部互链）+ index.md 总索引 + 说明文件（如 CLAUDE.md 告知 LLM 组织方式）（来源：[getaffineapp.com](https://getaffineapp.com/blog/what-is-llm-wiki)）
- 模型分工降本：摄取 3B-8B、编译 7B-14B、人工审核拒绝可带反馈重生成；Ollama 本机全离线（obsidian-llm-wiki）
- 规模红线：超上下文窗口（约 40 万词）后需混合检索补位——生成式不是取消 RAG，而是把检索对象从"原始分块"换成"编译后的结构化页面"
- 工具链 2026 升级：Obsidian 官方 obsidian-skills 已让 Claude Code/Codex 直接操作 Vault；Open Notebook 提供自托管 NotebookLM 形态；STORM 适合"给陌生领域画地图"但维护放缓

### 4.2.5 功能详解：WeKnora（腾讯）——三模式一体的双范式样本

- **基本信息**：腾讯开源（ima 开源内核），MIT，Go 后端+Vue3/TS 前端+Python 解析服务；Docker Compose/K8s/Lite 单二进制/桌面应用
- **三大核心能力共享同一知识库**：
  - **RAG 问答**：向量+BM25 混合检索、RRF 融合、Rerank；回答附原文引用可点击定位；多模态解析
  - **ReAct Agent**：自主规划多步任务（检索→联网→MCP 工具→沙箱）；长期记忆，对话可追加/分叉/回滚
  - **自动 Wiki**：从原始文档自动生成互链 Wiki+可视化知识图谱+版本回滚——生成式范式落地
- **企业级**：全栈私有化；多租户+RBAC；AES-256；可选 GraphRAG 增强
- **生态**：飞书/Notion/Confluence/语雀/钉钉/GitLab/RSS 直连；20+ 模型厂商按角色管理；RESTful API/CLI/MCP

# 第五部分：2025-2026 趋势研判（v5 新增）

**T1 Long-Context vs RAG：论战收敛于混合架构**。"RAG 已死"派（Gemini 2M 全量+提示缓存省运维）与反方（成本 10-20 倍、Context Rot 实测、权限/新鲜度属检索层）之争已 settle——<200K 全塞、200K-2M 看并发、>2M 必须 RAG；"RAG 定位 5000 相关 token，长上下文负责推理"成为生产默认（成熟度：已成共识）。

**T2 上下文工程成为一等学科**。Anthropic 2025-09 正式定义（compaction/结构化笔记/子代理/JIT 加载四技术），Claude 平台 context editing+memory tool GA（agentic search +39%、token -84%）；Chroma 自我重新定位为"context infrastructure"。上下文工程不是取代 RAG，而是把 RAG 变成自己的一环（成熟度：术语全行业采纳，工具链 GA）。

**T3 记忆操作系统化**。MemOS 的 MemCube 三态（明文/KV-cache/LoRA 参数）+调度器把记忆当一级资源；Mem0 68k★成为生产事实标准；TencentDB Agent Memory 把 LLM-Wiki 当记忆资产——记忆系统与知识库边界消失，企业应"文档知识走 RAG、行为知识走记忆、MCP 互访"（成熟度：强研究弱商用，生产选 Mem0/Letta/Cognee）。

**T4 Deep Research 与知识库内外合流**。OpenAI/Perplexity/Gemini 的 deep research（规划→多轮搜索→带引用长报告）正从公网调研演化为内外混合知识检索：Gemini Deep Research API 支持 MCP 与文件检索、OpenAI 可接 Drive/SharePoint 只读——多子代理+引用审计模式可直接移植到企业知识库（成熟度：消费级成熟，企业 API 化刚起步）。

**T5 推理模型×检索**。o1/R1 类模型与 RAG 的结构性错配（推理链中途产生知识缺口）催生 Search-o1（多跳 +30%）、Search-R1（RL 学"何时搜"）、ReaLM-Retrieve（+10.1% F1 且检索调用 -47%）；综述分出 RAR/ReAR 两方向；落地税是"过度思考 token 膨胀"（成熟度：论文最热，工业以 prompt 级 agentic 检索为主）。

**T6 多模态 RAG 工业化（ColPali 路线）**。整页截图多向量+late interaction 免 OCR，视觉复杂文档准确率约 +50%；三种范式定型；真实落地已现（丹麦制造 Norm-Chatbot、增材制造缺陷检测）；瓶颈是存储成本（每页 ~1030 向量）与多页推理（成熟度：生产可用，"vision-first 成默认"是预判非事实）。

**T7 MCP 成为知识库的 Agent 接口事实标准**。2025-03 OpenAI 采纳、2025-12 捐赠 Linux 基金会后厂商中立；知识库封装 MCP server 是标准做法；KB 类 server 生态爆发（mcp-server-memory/Mem0 MCP/ApeRAG/Neo4j/Qdrant）；治理税：工具 schema 常驻上下文（5 server ~3000 token）、prompt injection 风险（成熟度：协议标准已定，安全治理不成熟）。

**T8 向量库市场整合与商品化**。Pinecone 被报道探讨出售（未成交，注意口径）+换帅转向"Agent 知识基础设施"；Weaviate 逆势 $50M C 轮押注 agentic 检索；Chroma Rust 重写+Cloud GA+混合检索转型；结构性原因：pgvector/ES 把向量变 checkbox——纯向量库窗口关闭，价值上移知识层/上下文层（成熟度：整合进行中）。

**T9 端侧个人知识库（NPU 路线）**。苹果（端侧语义索引+3B 模型+Private Cloud Compute）、荣耀（量化+统一向量化检索，信通院 L3，场景 200→3000+）、小米（澎湃 OS 意图框架）三路线分明；共性瓶颈：3nm 功耗散热限制端侧参数量、"端侧隐私 vs 云端能力"矛盾未解（成熟度：营销先行体验参差，2026-2027 真实竞争焦点）。

**T10 开源"归档潮"与生命周期治理**。2025-2026 h2oGPT、Verba、Reor、Vanna（23.8k★但只读）、pgvecto.rs 等一代明星项目相继归档/停更；Microsoft GraphRAG、STORM 维护放缓——**Star 数与可用性脱钩，选型必须查最近提交**。同时国产大厂开放程度分化：腾讯（WeKnora，MIT）> 字节（OpenViking，AGPL）> 阿里（仅示例仓库不开源产品）。

## 6.1 失败率统计（多方交叉，引用注意口径）

- RAND 对 2400+ 企业 AI 项目：失败率 ~80%（传统 IT 约 40% 的两倍）；根因五项：成功定义不清、数据债、未嵌入工作流、追技术而非结果、高层支持衰退（[alicelabs](https://alicelabs.ai/en/insights/enterprise-ai-roadmap-consulting)）
- MIT NANDA《The GenAI Divide 2025》：~95% 企业 GenAI 试点对损益无可测影响（[tomastc](https://tomastc.com/en/blog/generative-ai-implementation-pitfalls-2026-en)）
- Gartner（2026 年 1-4 月，1303 家企业）：仅 22% 实现跨 BU 规模化；预测 2026 年底前 60% 缺 AI-ready 数据项目将被放弃、>40% agentic AI 项目 2027 年底前取消；"Agent Washing"警示 >70% 企业级 Agent 项目可能 2029 前失败（[AIDIA](https://aidia.it/en/news/rag-retrieval-augmented-generation-architettura-dati-aziendali)）

## 6.2 RAG 特异性失败复盘（公开案例）

- **金融客服**：上线 6 周支持升级率 +34%——向量库 3 个月未重索引、引用过期利率；RAG 相关故障占生产 AI 问题 1/3-1/2（[channel.tel](https://www.channel.tel/blog/knowledge-base-bottleneck-why-rag-alone-isnt-enough-production-agents)）
- **法律科技**：18 万份合同"语义相似但法律不适用"——嵌入缺结构元数据、评测集由工程师构造；元数据过滤重建后覆盖率 100%→87% 换正确性（[simorconsulting](https://simorconsulting.com/blog/when-rag-failed-a-knowledge-retrieval-project-post-mortem)）
- **国内案例**：银行引用 2019 利率（同步延迟）；零售 top-5 命中 38%→82%（加 BM25+标签过滤）；金融 512 token 定长切断风险警示（[CSDN](https://blog.csdn.net/yiyiyi0322/article/details/165334921)、[zvenue](http://www.zvenue.cn/info/enterprise-rag-failure-modes.html)）
- 通用失败模式：过期数据无新鲜度信号、固定切片撕裂逻辑、检索空隙幻觉、新旧文档矛盾、精确数据走近似检索

## 6.3 ROI 度量与造价参考

- 麦肯锡 2025：78% 组织用 AI、74% 报告首年 ROI，但仅 39% 见到 EBIT 影响；~23% 大企业用向量库/RAG（[gmware](https://gmware.com/blog/institutional-knowledge-strategic-ai-assets)）；有效量化 AI 价值的企业 ROI 比不量化者高约 40%（四维：效率/决策质量/客户体验/合规风险）
- 成功要素量化：有事前指标 54% vs 无 12%；C-suite 持续支持 68% vs 11%；转型式定位 61% vs 18%；成功者 47% 预算投基础（数据/治理/变革）vs 失败者 18%（[ifactoryapp](https://ifactoryapp.com/blog/genai-pilot-to-production-80-percent-failure-manufacturing)）
- 造价区间：单域试点 $15-60K；2-4 源生产系统 $60-200K；企业平台 $200K+（另计推理月费与治理人力）
- 成功数据点：Glean 客户 Booking.com 全员 14000 人、Zillow 周省 1.5+ 小时/采用率 80%；FastGPT 投研自动化率 90%+/客服转人工 -42%；腾讯乐享旷真律所月访问 40 万人次/满意度 93 分（厂商口径，注意自报偏差）

# 第七部分：行动建议与风险

1. **按三线分流再谈架构**：原文问答走检索式、知识沉淀走生成式、Agent 行为知识走记忆系统；三线通过 MCP 互访是企业知识中枢的合理终态
2. **检索式从数据治理与评测集起步**：50 份核心文档 + 100 条真实问题基线 + 引用硬指标；组件用 2026 年新默认（Qwen3-Embedding/Reranker、混合检索、RAGAS+DeepEval 进 CI/CD）
3. **长上下文按决策树使用**：<200K 全塞、200K-2M 看并发成本、>2M 必须 RAG；不要为"免 RAG"支付 10-20 倍 token 账单，也不要忽视 Context Rot
