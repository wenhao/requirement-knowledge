# AI Coding 与 SDD 需求适配与落地方案

> **方案定位**：当前的问题已经不是"AI 能不能写代码"，而是"**哪些需求可以直接交给 AI Coding、哪些必须先走 SDD、哪些要先做需求澄清与知识治理，再谈自动化**"。本方案给出一套可打分、可决策、可直接落地的完整方法，并与本仓库的需求知识库建设形成上下游闭环。

## 一、背景与核心结论

### 1.1 两个概念的边界

| 概念 | 定义 | 人审对象 | 典型工具形态 |
|---|---|---|---|
| **AI Coding** | 把编码任务直接交给 AI Agent 执行：补全、生成、重构、修 Bug、写测试、迁移。人提供意图与上下文，审查代码结果 | 代码 Diff 与测试结果 | IDE 内 Agent、CLI Agent、代码评审机器人 |
| **SDD（Spec-Driven Development，规格驱动开发）** | 先把需求写成结构化、可验证的规格（Spec），评审通过后 AI 按规格逐任务执行。人审"规格"而非逐行审代码 | 需求 Spec 与技术 Spec | GitHub Spec Kit、Amazon Kiro、各 IDE 的 Plan/Spec 工作流 |

两者不是替代关系：**SDD 是 AI Coding 的"输入治理层"**。需求越模糊、影响面越大，越需要先花成本把 Spec 写清楚；需求越明确、验证越快，越可以直接 AI Coding。

### 1.2 核心结论（先给答案）

1. **决定适配度的是需求的六个就绪属性**：格式结构化（Markdown 优先）、内容清晰完备（意图清 + 规则全）、验收可判定（Given/When/Then）、知识支撑（术语统一、知识库有据可查）、**技术可行性（开发补充方案、指标、边界、异常）**、粒度适中（可拆 ≤1 人日任务）。**Markdown 不是形式主义，而是 AI 的输入协议；技术可行性没补齐，AI 只会"自信地写错方向"。**
2. **小而明确 → 直接 AI Coding**；**大而规则明确 → SDD**；**模糊或口径冲突 → 先需求澄清**；**红线领域 → AI 辅助但人主导**。
3. **SDD 的价值随需求粒度与影响面增大而增大**：它把人的评审从"代码层"前移到"意图层"，一次 Spec 评审代替多次代码返工。**AI Coding 的价值随验证速度加快而增大**：测试越快、反馈越短，AI 迭代效率越高。
4. **不适合的需求往往不是"AI 不行"，而是"知识没准备好"**：历史需求、术语口径、业务规则缺失时，任何模型都会产出"正确而通用"的空话——这正是本仓库需求知识库要解决的问题。

## 二、需求 AI 就绪度六维模型

模型只回答一个问题：**这份需求本身是否已经"AI 就绪"——能否被 AI 直接、高效、无歧义地消费**。

### 2.1 模型总览

一句话记忆：**格式对、需求清、验得出、有据查、能落地、拆得开**（"需求清"= 意图清 + 规则全；"能落地"= 方案行 + 指标明 + 异常有解）。

| # | 维度 | 一句话判断 | 权重 |
|---|---|---|---|
| 1 | 格式结构化 | 是否 Markdown 结构化，可直接入 Git | 10% |
| 2 | 内容清晰完备 | 为什么做、给谁做、做到什么程度、不做什么；规则可判定、边界有约定 | 30% |
| 3 | 验收可判定 | 验收是 Given/When/Then，可映射自动化测试 | 25% |
| 4 | 知识支撑 | 术语口径统一，知识库有同类需求/规则/决策可引用 | 10% |
| 5 | 技术可行性 | 技术方案、技术/性能指标、边界条件、异常处理已由开发补充且可行 | 15% |
| 6 | 粒度适中 | 已拆解或可拆解为 ≤1 人日的独立任务 | 10% |

### 2.2 定义与打分标准

| 编号 | 维度 | 英文 | 权重 | 5 分标准 | 1 分信号 |
|---|---|---|---|---|---|
| 1 | 格式结构化 | Structured Format | 10% | Markdown/纯文本；标题分级、表格、编号规则、链接可点、可直接入 Git | 扫描 PDF、截图、聊天记录、口头需求 |
| 2 | 内容清晰完备 | Clear & Complete Content | 30% | 背景、目标、用户、范围与非目标明确；业务规则编号化、每条可判定真假；边界/并发/兼容有约定 | 只有标题式一句话，目的与范围靠猜；"智能一点""体验要好"；关键边界未提 |
| 3 | 验收可判定 | Evaluatable Acceptance | 25% | 每条验收写成 Given/When/Then，可映射自动化测试 | 无验收，或只能靠主观感受验收 |
| 4 | 知识支撑 | Knowledge Grounding | 10% | 术语口径统一；需求知识库有同类需求、业务规则、决策条目并在 Spec 中引用 | 同名不同义；知识只在老员工脑中 |
| 5 | 技术可行性 | Technical Feasibility | 15% | 开发已补充技术方案与约束：关键技术/性能指标量化（P99、容量、兼容）；边界条件与异常处理（超时、降级、回退、幂等）有解；在现有架构下可实现 | 未做技术评估；性能与容量指标缺失；异常与降级未考虑；方案不可行或依赖未就绪 |
| 6 | 粒度适中 | Right Granularity | 10% | 已拆解或天然可拆为 ≤1 人日任务，每任务有独立验收 | 巨型需求无从下手；任务间强耦合 |

### 2.3 路由规则

| 加权总分 | 需求粒度 | 建议路由 | 说明 |
|---|---|---|---|
| ≥ 4.0 | 小（≤ 1 人日、单模块） | **A：直接 AI Coding** | 六维就绪 + 小任务，附意图、方案要点与验收即可 |
| ≥ 3.5 | 大（> 1 人日或跨模块） | **B：SDD 全流程** | 就绪度高但规模大，先 Spec 评审与任务拆解，再逐任务执行 |
| 2.5 – 3.4 | 任意 | **C：人主导 + AI 辅助** | Spec 只锁定关键决策与验收，AI 辅助实现 |
| < 2.5 或任一维 ≤ 2 | 任意 | **D：先就绪化** | 先补齐对应短板（转 Markdown、补内容、补技术方案与指标、补 Given/When/Then、补知识、拆任务），重评后再路由 |

## 三、需求路由决策流程

每个新需求进入团队时，按以下决策树路由（10 分钟内完成初判，争议时由产品 + 开发裁定）：

```text
S1 需求是否已是结构化文档（Markdown/表格/编号）？
 ├─ 否 → 就绪化：转为 Markdown 结构 → 回到 S1
 └─ 是 → S2 意图、规则、边界、非目标是否闭环？
      ├─ 否 → 需求澄清（AI 生成澄清问题清单 + 检索需求知识库）
      └─ 是 → S3 术语口径是否统一、知识库是否有支撑条目？
           ├─ 否 → 知识补齐：术语裁决 + 知识库条目 + Spec 引用
           └─ 是 → S4 开发是否已补充技术方案、技术/性能指标、异常处理？
                ├─ 否 → 技术补充：方案约束 + 指标量化 + 边界异常有解
                └─ 是 → S5 六维就绪度打分 + 需求规模判断
                     ├─ ≥4.0 且 ≤1 人日        → A 直接 AI Coding
                     ├─ ≥3.5 且 >1 人日/跨模块 → B SDD 全流程
                     ├─ 2.5–3.4                → C 人主导 + AI 辅助
                     └─ <2.5 或任一维 ≤2       → D 先就绪化，重评后再路由
```

### 七步操作要点

1. **格式就绪**：先确认需求已是 Markdown 结构（标题、表格、编号），否则先转换；
2. **内容闭环**：意图、规则、边界、非目标逐项检查，缺口用 AI 澄清问题清单补齐；
3. **验收先行**：每条验收写成 Given/When/Then，并确认可映射自动化测试；
4. **知识支撑**：统一术语口径，在 Spec 中引用知识库条目作为依据；
5. **技术先行**：由开发补充技术方案与约束，量化技术/性能指标，明确边界条件与异常处理（超时、降级、回退、幂等）；
6. **打分路由**：用六维评估表打分，任一维 ≤2 先补齐对应短板，再定 A/B/C/D；
7. **记录决策**：路由结论与理由记录在需求条目上，沉淀为组织经验。

## 四、SDD 落地流程与模板

### 4.1 总流程（十步闭环）

```text
①需求澄清 → ②需求Spec编写 → ③需求Spec评审
    → ④技术Spec编写 → ⑤技术Spec评审
    → ⑥任务拆解（L3） → ⑦AI逐任务执行
    → ⑧自动化验证 → ⑨人工终审 → ⑩验收与知识回写
```

| 步骤 | 责任人 | 关键产出 | 通过标准 |
|---|---|---|---|
| ① 需求澄清 | 产品 + 开发 | 澄清问题清单与答案 | 业务口径一致、边界明确 |
| ② 需求 Spec | 产品 | 用户故事、业务规则、验收标准 | 每条规则可判定真假 |
| ③ 需求 Spec 评审 | 产品 + 开发 | 评审结论 | 验收标准可执行、无开放冲突 |
| ④ 技术 Spec | 开发 | 方案、数据模型、API、测试策略 | 有备选方案对比与回滚方案 |
| ⑤ 技术 Spec 评审 | 技术经理 | 评审结论 | 安全、性能、迁移风险有结论 |
| ⑥ 任务拆解 | 开发 | 有序任务清单（每任务 ≤ 0.5–1 天） | 每任务有独立验收 |
| ⑦ AI 执行 | 开发（人对结果负责） | 代码 + 测试 + 文档 | 逐任务提交，禁止一次性大爆炸 |
| ⑧ 自动化验证 | CI | 测试/静态检查/安全扫描报告 | 全绿，覆盖率不下降 |
| ⑨ 人工终审 | 开发 | 审查意见 | Diff 与 Spec 逐条对照 |
| ⑩ 验收与回写 | 测试 + 产品 | 验收记录、知识库更新 | 新规则/决策/术语回写知识库 |

### 4.2 Spec 分层（L0–L3）

| 层 | 名称 | 生命周期 | 内容 | 变更频率 |
|---|---|---|---|---|
| **L0** | 项目宪法（Constitution） | 全项目长期有效 | 技术栈、目录结构、编码规范、测试要求、性能预算、安全红线 | 极少变更，变更需开发评审 |
| **L1** | 需求 Spec | 单个需求 | 用户故事、业务规则、边界与异常、验收标准、非目标 | 随需求演进 |
| **L2** | 技术 Spec | 单个需求 | 方案概述、架构改动、数据模型、API 契约、异常降级、测试策略、回滚 | 随方案演进 |
| **L3** | 任务计划（Plan/Tasks） | 单个需求的执行期 | 有序任务列表，每任务含前置、涉及文件、验收、风险 | 随执行更新 |

> **AI 执行时的上下文组装**：`L0 宪法 + L1 需求 Spec + L2 技术 Spec + 当前任务（L3 中的一项）+ 相关代码/知识库条目`。不要一次性注入全站知识，按需检索。

### 4.3 工具链选型原则（不绑定产品）

1. **Spec 必须以纯文本入库**（Markdown/YAML），不锁死在任何工具的私有格式里；
2. 模板可由 Spec Kit、Kiro、IDE Plan 模式等工具生成，但**评审权永远在人**；
3. 每个 PR 必须关联 Spec 链接与任务编号，做到"代码可追溯到规则"；
4. Spec 是活文档：需求变更时，Spec 与代码在同一个 PR 中更新；
5. AI Agent 必须能读取 L0–L3 与知识库检索结果，否则不允许开工。

### 4.4 角色与职责（RACI）

| 活动 | 产品 | 开发（兼任架构） | 测试 | 技术经理 |
|---|---|---|---|---|
| 需求澄清 | A | R | C | I |
| 需求 Spec 编写 | A/R | C | C | I |
| 需求 Spec 评审 | A | R | C | I |
| 技术 Spec 编写 | I | A/R | C | C |
| 技术 Spec 评审 | I | R | C | A |
| 任务拆解 | I | A/R | C | C |
| AI 执行 | I | A/R | I | I |
| 代码终审 | I | A/R | C | C |
| 验收 | C | C | A/R | I |
| 知识回写 | A | R | I | I |

（A=负责拍板，R=负责执行，C=需咨询，I=需知会）

## 五、与需求知识库的闭环

SDD 的上限取决于上下文质量，而上下文来自需求知识库。两者形成双向闭环：

```text
【写 Spec 前】需求知识库
   ├─ 检索历史同类需求 → 复用规则与边界用例
   ├─ 检索术语口径 → 避免"同名不同义"
   ├─ 检索业务规则与决策 → 防止新需求与存量逻辑冲突
   └─ 检索风险与争议证据 → 提前规避已知坑
          ↓ 注入
【Spec 编写与评审】L1 需求 Spec / L2 技术 Spec
          ↓ 执行与验收
【交付后回写】新增规则、决策、术语变更、FAQ
   └─ 回写需求知识库 → 沉淀为组织资产 → 供下一个需求复用
```

落地要求：

1. 需求 Spec 中的每条业务规则标注知识库来源条目（或标记"新增"）；
2. 评审发现的口径冲突，先在知识库中裁决，再回到 Spec；
3. 交付后一周内完成知识回写，由产品审核；
4. 知识库中沉淀的"需求模板 + 边界用例清单"，反过来加速下一个 Spec 的编写。

## 六、度量与验收标准

| 指标 | 定义 | 试点目标 | 采集方式 |
|---|---|---|---|
| Spec 一次评审通过率 | 首次评审无重大返工的比例 | ≥ 70% | 评审记录 |
| 任务一次通过率 | AI 生成任务无需返工的比例 | 初期 ≥ 40%，稳定后 ≥ 60% | 任务看板 |
| 验收标准自动化率 | 验收条款可映射为自动化测试的比例 | ≥ 80% | Spec 与测试映射表 |
| 需求澄清返工次数 | 开发中因需求模糊被打回的次数 | 较基线下降 ≥ 50% | 需求条目日志 |
| 缺陷逃逸率 | 上线后缺陷 / 总缺陷 | 不高于人工基线 | 缺陷系统 |
| 交付周期 | 需求确认到验收的时长 | 较基线缩短 ≥ 30% | 项目管理工具 |
| 知识回写率 | 交付需求回写知识库的比例 | ≥ 90% | 知识库审计 |

**试点验收门槛**：连续 4 周，任务一次通过率 ≥ 40%、缺陷逃逸率不高于基线、知识回写率 ≥ 90%，方可进入推广阶段。
